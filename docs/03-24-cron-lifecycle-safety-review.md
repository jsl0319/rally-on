# 크론 활성화 전 정책·안전성 재검토


> 이 문서의 1~5절은 활성화 전 감사 기록이다. 이후 승인·보완·검증은 6~7절, 최종 운영 활성화 결과는 [03-23](03-23-free-cron-operations.md)의 마지막 절을 따른다.

확인: 2026-10-10 KST. 기준 코드 `cc7de5d`.
사용자는 실제 운영 상태 정리·자동 실행을 승인하면서, 대관 진행 여부에 미치는 영향과
1분 무료 실행 가능성을 먼저 검토하도록 요청했다. 이 문서는 현행 동작과 제안을 구분한다.
**Cloudflare 예약 실행은 미활성 상태 유지. 운영 상태 변경 테스트도 이번 검토에서는 실행하지 않았다.**
기존 Vercel 일일 크론과 요청 시 상태 보정은 계속 존재한다. Cloudflare만 껐다고 현행 자동 취소가 전부 멈춘 것은 아니다.

## 결론

15분 주기는 비용 절충안이지 중요한 진행 판정에 최적인 방식이라고 단정할 수 없다.
1분 호출만으로 사람의 확인 누락·장애 후 소급 취소·오래된 화면·알림 전달 문제는 해결되지 않는다.
금전/일정의 안전장치를 먼저 보완한 뒤 주기를 정한다. 사업 규칙을 몰래 변경하거나
무료 보장을 위해 장애 가능성을 숨기지 않는다.

## 1. 현재 자동 처리 범위

| 처리 | 실제 기준 | 크론이 바꾸지 않는 것 |
| --- | --- | --- |
| 미확정 신청 만료 | 이체 기한 + 30분의 운영자 확인 기한 도달. 기존 기록은 고지된 기한 유지 | 실제 통장 입금 여부를 자동 조회하지 않음 |
| 최초 경기 진행 판정 | 시작 3시간 전까지 **참가 확정**된 사람의 총원/성별 구성 | 입금 알림이나 수령 기록만으로 참가 확정하지 않음 |
| 추가 신청 마감 | 시작 90분 전 | 기존 승인자의 이체 T−60분, 확인 T−30분 유지 |
| 진행 판정 통과 후 인원 부족 | 자동 전체 취소하지 않고 운영자 조치 필요 | 나중 취소를 이유로 최초 진행 판정을 뒤집지 않음 |
| 일반 매칭·채팅 | 시작 시 마감/미성사 처리, 종료 24시간 뒤 채팅 읽기 전용 | 은행 송금·외부 대관 예약/취소 없음 |

판정 기준 시각과 실제 작업 실행 시각은 다르다. 예를 들어 19:10 경기의 판정 기준은
16:10이고, 15분 예약이 16:15에 실행되어도 16:10까지 확정된 인원을 기준으로 한다.
단, 해당 API의 모든 기한은 서버에서 직접 재검사하므로 크론이 늦었다고 5분의 추가 확정 시간을 주지 않는다.

## 2. 활성화 전에 해결할 운영 위험

### A. 정시 입금과 참가 확정의 두 단계 사이에서 만료 가능

`recordCourtReceipt`는 수령 금액/시각을 저장하고, `confirmCourtMatchDeposit`가 별도로 참가를 확정한다.
`expireOverdueDeposits`는 수령액·입금 알림 유무와 무관하게 확인 기한에 도달한 ACCEPTED를 만료한다.
따라서 실제 입금과 앱의 수령 기록이 있어도 확정 버튼을 놓치면 만료·최소 구성 미달 취소가 가능하다.
이는 현재 확정 인원만 세는 정책대로의 동작이지만 운영 사고 위험이다. 1분 주기로 바꿔도 동일하다.

**권장:** 정상 입금은 ‘입금 기록하고 참가 확정’을 한 트랜잭션으로 처리한다.
부족/늦은 입금·종료 건의 수령 기록은 현재처럼 분리한다. 참가자의 ‘입금했어요’만으로
자동 확정하지 않는다. 운영자가 아예 기한 내 대조하지 못한 건의 유예/수동 판정 정책은
별도 결정이 필요하며 무기한 대기로 바꾸면 다른 참가자도 일정을 정할 수 없다.

### B. 장시간 장애 후 경기 종료 뒤에도 최초 자동 취소 가능

`reconcileCourtMatches`는 OPEN/CLOSED 전체를 가져오고, 미달 판정에는 시작/종료 이후의
소급 취소를 막는 상한이 없다. 현장에서 별도로 진행했는지 시스템이 알 수 없는 상태에서도
미판정 경기를 취소하고 전액 반환 대상으로 만들 수 있다.

**권장:** 최소한 시작 시각이 지난 미판정 경기는 자동 취소 대신 운영 확인 대상으로 남긴다.
그 상태를 자동 ‘정상 진행’으로 간주해서도 안 된다. 운영자가 실제 제공 여부를 확인하고
근거를 남겨 처리하도록 한다. 이는 기존 자동 취소 정책의 예외를 추가하는 변경이므로
정책 합의가 필요하다. 크론만 고치면 조회 API에서도 같은 문제가 생기므로 공통 판정 함수에 적용해야 한다.

### C. 서버 처리와 사용자에게 보이는 결과가 다를 수 있음

운영자 참가자 관리와 참가자 상세는 최초 로드/일부 버튼 동작 후 갱신한다.
열어 둔 화면은 판정 시각·탭 복귀에 자동 갱신되지 않는다. 크론이 취소를 완료해도
오래된 ‘모집 중’/‘참가 확정’을 보고 대관·이동을 결정할 수 있다.

**권장:** 예정 판정 시각과 탭 복귀에 다시 조회하고, 확인 시각·오류/오래된 상태를 명시한다.
개인 참가 확정과 경기 진행 판정은 계속 별개로 표시한다. 상시 초 단위 폴링이나 새 화면은 필요 없다.

### D. 알림 생성이 실제 연락을 뜻하지 않음

현재 알림은 DB에 저장하는 앱 내 알림이다. 취소/거래 알림은 설정과 무관하게 남기지만
앱 밖 푸시·문자·카카오 전송이나 읽음 보장은 없다. 판정 통과는 DB에 기록하고 화면에
보여 주지만 별도의 경기 진행 확정 알림은 없다.

**권장:** 판정 결과를 운영자·참가자에게 명시하고, 파일럿 동안 운영자가 판정 시각에
앱에서 결과를 확인하도록 한다. 앱을 열지 않은 사람도 제때 연락받아야 한다면 전달 채널을
추가해야 한다. 무료 크론만으로 정시 통보가 보장됐다고 안내하지 않는다.

### E. 한 경기 오류가 뒤의 전체 처리를 막음

코트 배치의 반복문에는 경기별 오류 분리가 없어 한 건이 계속 실패하면 뒤의 코트 경기와
일반 매칭·채팅 정리까지 실패할 수 있다. 모든 미래 경기와 이미 시작한 CLOSED도 읽어
매번 잠근다. 또한 순서/배치 한도가 없다. 소규모라도 한 비정상 행 때문에 반복 실패할 수 있다.

**권장:** 경기별 오류를 분리하고 처리 필요 시각 순으로 작은 묶음을 실행한다.
실패가 있으면 전체 성공으로 표시하지 않고 실패 건수/안전한 식별정보를 남긴다.
최근 성공과 연속 실패를 확인할 최소 수단을 둔다. 대규모 작업 큐나 자동 송금 시스템은 필요 없다.

### F. 앱 경기 취소와 외부 대관 취소는 별개

3시간 전은 앱 참가 구성 판정 시각이다. 코트의 실제 대관 취소 기한·취소 수수료와
자동으로 일치하지 않으며, 앱의 취소는 외부 예약을 취소하지 않는다. 운영자가 자기 시설을
제공하는지, 타 시설을 예약해 제공하는지에 따라 손실이 달라진다. 운영자는 이 판정 시각으로
실제 공급을 결정할 수 있는 시간만 공개해야 한다. 코트별 외부 계약을 앱이 보장하지 않는다.

## 3. 이미 확보된 안전장치

- 신청·입금 확정·취소와 크론은 같은 Match 행 잠금을 사용한다. 잠금을 얻은 뒤 시각을 읽는다.
- 참가 확정 수는 실제 판정 시각 기준으로 계산한다. 지연 실행 중 이후 개인 취소가 발생해도 과거 구성을 보존한다.
- 판정 통과 후 참가 취소는 전체 자동 취소로 뒤집지 않는다.
- 만료/취소와 필수 알림이 같은 트랜잭션으로 기록된다. 재실행은 이미 바뀐 상태를 반복 처리하지 않는다.
- 늦게 확인된 실제 입금은 종료 상태에서도 기록하고 반환 대상으로 유지한다. 크론이 자동 송금하지 않는다.
- 외부 Worker 전용 키·HTTPS 고정 경로·리디렉션 차단·200/status 검사·실패 기록을 구현했다.

## 4. 1분 무료 운영 가능성

공식 조건 확인일 2026-10-10. 30일·현재 0.25 CU 컴퓨트·호출 후 5분 활성 가정의 계산이다.

| 주기 | 하루 호출 | 30일 호출 | 크론 때문에 활성화되는 Neon 예상 사용량 |
| --- | ---: | ---: | ---: |
| 1분 | 1,440 | 43,200 | 약 180 CU-hours |
| 5분 | 288 | 8,640 | 약 180 CU-hours |
| 10분 | 144 | 4,320 | 약 90 CU-hours |
| 15분 | 96 | 2,880 | 약 60 CU-hours |

31일이면 각각 186/186/93/62 CU-hours. 사용자 트래픽·개발 브랜치·실제 중지 지연을
포함하지 않은 추정이며 특히 10분의 여유는 작다. 데이터가 없어도 매번 DB를 깨우면 같은 문제가 생긴다.

- **Cloudflare 단독:** 1,440회/일은 무료 100,000회/일 안이다. CPU 10ms 제한과 실제 실행 실패는 별도 확인한다. 네트워크 대기는 CPU 시간과 다르다.
- **Neon:** 무료는 프로젝트당 월 100 CU-hours. 매분 실제 DB 조회하는 현 구성은 정상적으로 계속 실행되면 무료 한도를 초과하므로 권장할 수 없다. 단순히 ‘조회가 빠르다’거나 ‘이용자가 적다’는 이유로 해결되지 않는다.
- **Vercel:** 43,200 호출은 Hobby 100만 호출 안이지만 CPU 4시간·메모리 360GB-hours·앱의 다른 사용량도 합산된다. 실제 CPU/대기 사용량 측정 없이 전체 무료를 보장하지 않는다. 현재 계정은 Hobby이며 상업 운영 허용 여부는 크론 비용과 별도로 해결해야 한다.

**선택지:**

1. 안전장치 후 15분 + 요청 시 즉시 판정: 가장 단순하고 무료 여지가 크지만 무접속 자동 처리 지연을 받아들여야 한다.
2. 중요한 경기 진행 판정까지 1분 수준이 필요하면, Worker는 매분 실행하되 미리 저장한 다음 처리 시각에만 DB를 호출하는 방식을 설계한다. 일정 추가/변경 누락 방지와 주기적 재대조·장애 복구가 필요하다. 무료 가능성을 높이지만 지금 Worker에 주기만 바꾸는 작업은 아니며 사용량 보장도 아니다.
3. 현재 구조 그대로 안정적인 상시 1분 호출을 원하면 DB 무료 한도를 늘리는 방안을 검토한다. 유료 전환은 별도 승인 사항이다.

공통으로 1분 주기도 정각 실행/통보 SLA가 아니다. 신청/확정의 서버 기한 검증을 제거하지 않는다.
무료만 맞추려고 밤 시간에 무조건 정지하면 이른 오전 경기 판정이나 입금 확인 만료를 놓칠 수 있어 제외한다.

## 5. 이번 재현·범위와 다음 작업

전용 로컬 PostgreSQL에서 임시 감사 테스트 3개를 실행하여 아래 현행 동작을 확인했다.

1. 정시 수령 36,000원 기록 → 참가 확정 미완료 → 판정 시각에 신청 만료·경기 취소·36,000원 반환 대상.
2. 1명만 확정된 최소 2명 경기 → 무접속/장애 가정 → 종료 1시간 뒤 첫 배치에서도 전체 취소·전액 반환 대상.
3. 판정 때 2명 확정, 그 뒤 1명 개인 취소 → 14분 늦은 배치 → 최초 2명 구성 통과 보존.

3개 모두 현재 동작을 재현했다. 위험 동작을 바람직한 회귀 규칙으로 고정하지 않도록 임시 테스트는
검토 후 제거했으며, 후속 수정 때 원하는 경계 동작의 정식 회귀 테스트를 추가한다.
직전 단위의 중복 배치·재실행 검증(코트 DB 78개/전체 단위 408개)은 별도 기존 결과다.
실제 Cloudflare 예약 실행과 알림 전달·실기기 최신 화면은 아직 검증하지 않았다.

권장 순서: **입금 기록/확정 원자화와 늦은 자동 취소 보호 정책 → 최신 진행 상태 표시 및 실패 분리 → 실행 주기/사용량 검증 → 실제 예약 활성화**.
시작 이후 미판정 건의 수동 처리 예외와 외부 전달 채널은 정책 변경이므로 확정 전 임의 적용하지 않는다.
사용자의 기존 자동 실행 승인은 유지하며 같은 승인을 반복 요청하지 않는다.

근거: [Cloudflare 제한](https://developers.cloudflare.com/workers/platform/limits/),
[Cron 실행](https://developers.cloudflare.com/workers/configuration/cron-triggers/),
[Neon 무료 사용량](https://neon.com/blog/neon-free-plan-1-gb-per-project),
[Neon 자동 중지](https://github.com/neondatabase/website/blob/main/content/docs/introduction/scale-to-zero.md),
[Vercel Hobby 한도·용도](https://vercel.com/docs/plans/hobby).

## 6. 사용자 결정과 안전장치 반영 (2026-10-10 후속)

- 사용자는 A/B/C/E의 권장 보완을 승인했다. 진행 여부를 협의로 정하는 대안을 검토한 뒤 **기존 시작 3시간 전 자동 판정 유지**를 선택했다. 90분 협의 마감안은 채택하지 않았다.
- 정상 입금의 수령 기록·참가 확정·채팅 멤버십·확정 알림은 같은 트랜잭션에서 저장한다. 부족/늦은 입금, 종료 신청, 인계 담당자의 수령 기록은 참가를 복구하지 않는다. 기존 확정 API의 동일 상태 재시도는 성공 결과를 반환하되 추가 알림을 만들지 않는다.
- 시작 시각 이후 최초로 발견된 미판정 경기는 전체 자동 취소를 하지 않는다. `REVIEW_REQUIRED`를 파생해 표시한다. 기존 확인 기한 만료는 유지되며, 미확정 종료 건의 실제 입금은 기존 전액 반환 규칙을 따른다.
- 운영자만 `/operator/court-matches/{id}`에서 실제 미제공 취소 또는 일정 종료 후 제공 완료를 기록한다. 근거·처리자·요청 ID·시각을 기존 `courtCompositionSnapshot.lateReview`에 저장한다. 자동 판정을 통과한 것처럼 과거 확정 시각을 만들지 않는다. 미제공 취소는 남은 활성 신청의 실제 입금액을 반환 대상으로 하고 이전 개인 취소 기준은 유지한다. 일부 제공은 완료 확인 후 기존 합의 반환 기능을 사용한다.
- 운영자/참가자 상세는 최초 진입·탭 복귀·네트워크 복구·판정 및 개인 기한에 재조회한다. 상시 폴링하지 않는다. 마지막 확인 시각과 재조회 실패 시 이전 정보임을 표시한다. 오래된 응답이 새 응답을 덮지 않도록 제어하고 편집 중 입력은 일반 재조회만으로 초기화하지 않는다.
- 코트 배치는 필요한 경기 ID만 일정 순으로 읽고 한 경기씩 잠금/커밋한다. 한 건 실패는 분리하며 일반 매칭·채팅 정리를 계속한다. 35초가 지나면 새 경기 처리를 시작하지 않고 미처리 건수를 반환한다. 실패/미처리가 있으면 HTTP 500으로 스케줄러에 실패를 알린다. 이미 진행 중인 DB 호출을 강제 중단하는 전체 실행 시간 보장은 아니며, 대량 누적은 파일럿 로그에서 확인한다.
- 푸시는 별도 조사·제안 단계다([03-25](03-25-web-push-pilot-proposal.md)). 사용자 동의 강제/접근 제한·외부 전송·새 프로덕션 의존성은 적용하지 않았다.
- Cloudflare 크론은 계속 비활성 상태로 검증한다. 기존 자동 실행 승인은 유효하지만, 이 변경의 운영 배포/실행 검증 완료 전 활성화하지 않는다.

## 7. 후속 검증 결과

- 단위 테스트 410개, 전용 로컬 DB의 코트 매칭/금융 보존 테스트 99개 통과.
- 모바일 E2E 3개 통과: 한 번의 입금 저장으로 확정, 참가자 복귀 갱신과 503 오류의 이전 정보 경고, 확인 기한 자동 갱신, 지연 경기의 미제공 확인/취소. 비로그인 401·근거 누락 422도 확인했다.
- E2E에서 수동 확인 select의 라벨 탐색 문제를 확인해 명시적인 label-for/id로 수정하고 해당 흐름을 다시 통과했다. 390px 스크린샷을 확인했고 가로 넘침·브라우저 런타임 오류가 없었다.
- TypeScript·린트·프로덕션 빌드 통과. DB 스키마 변경이나 새 의존성은 없다.
- 실제 휴대전화의 푸시 수신은 이번 구현 범위가 아니며 검증하지 않았다. 운영 배포와 예약 실행 결과는 03-23의 활성화 기록에 별도로 남긴다.
