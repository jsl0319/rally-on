# 코트 매칭 모바일 흐름 검증

## 1. 목적과 범위

2026-10-04 사용자 승인에 따라 코트 매칭의 최초 설정부터 참가 신청·입금 확인·채팅·취소·환불까지 모바일 화면에서 연결해 검증한다. 정본 정책은 [운영자 주최 모델](03-2-court-match-operator-hosted-redesign.md), [금전 처리](03-7-court-match-money-operations.md), [연락처](03-15-court-operator-contact.md), [기본정보 재사용](03-16-court-provider-information-design.md)을 따른다.

- 실제 신규 Court·Slot·Match·신청·수령·환불 기록은 전용 로컬 E2E DB에서 만든다. 운영 데이터는 사용하지 않는다.
- 카카오 로그인과 사업자·시설 심사만 인증된 테스트 계정과 승인 기록으로 대체한다. 가입·외부 심사 자체의 성공을 검증한 것은 아니다.
- 계좌이체·환불은 테스트 금액과 기록으로 처리한다. 실제 은행 송금은 수행하지 않는다.
- 크론은 계속 보류한다. 실행 주기나 외부 스케줄러를 변경하지 않는다.

## 2. 연속 검증 경로

신규 테스트: `tests/e2e/court-mobile-journey.spec.ts`.

브라우저는 터치 입력을 지원하는 모바일 Chromium 환경이다. 390px 기본 화면과 320px 작은 화면의 가로 넘침을 확인한다. 320×480의 줄어든 화면에서 마지막 입력란·동의·저장·신청·환불 계좌에 접근하는지도 확인한다. 이는 실제 iOS·Android 키보드 동작을 대체하지 않는다.

## 3. 발견한 문제와 수정

### 과거 운영 방식이 남은 안내

심사 완료·운영 홈·시간 관리에는 운영자가 시간을 공급하고 일반 모집자가 별도로 참가 신청을 받는다는 예전 안내가 남아 있었다. 현재는 운영자가 코트 매칭을 공개하고 설정한 승인 방식과 입금 대조로 참가자를 관리한다. 관련 안내를 현재 흐름으로 맞췄다. 빈 목록의 `전체 비용` 표현도 실제 입력 항목인 `1인 참가비`로 바꿨다.

변경 파일:

- `src/features/partner/operator-application-status.tsx`
- `src/features/partner/operator-time-management.tsx`

### 좁은 운영자 목록의 줄바꿈

390px 캡처에서 상태 배지의 `공개·모집 중`과 `10:00–12:00`이 중간에 끊어졌다. 상태 배지를 축소하거나 내부에서 줄바꿈하지 않게 하고, 공간이 부족하면 카드 머리말의 다음 줄로 배치한다. 일자와 시간 범위를 별도 단위로 표시해 시간 숫자를 나누지 않는다. 목록 제목도 `코트 매칭 관리`로 줄였다.

API·데이터 구조·기한·승인·취소·환불 정책은 변경하지 않는다. 신규 의존성과 마이그레이션도 없다.

## 4. 검증 결과 (2026-10-04)

- 시작 기준: `main`의 `e2849f1`, 기존 작업 트리는 깨끗한 상태였다.
- 수정 전 코트 관련 브라우저 시나리오 18개 통과. 수정 후 기존 18개와 신규 연속 경로 1개, 총 **19개 통과**.
- 관련 시나리오는 연락처의 등록·재사용·충돌·공개 중단·권한, 신청 당시 안내 기록, 경기 구성, 취소 금액 재확인, 운영자·참가자 탈퇴 후 거래 처리를 포함한다.
- 신규 경로의 페이지 실행 오류 0건. 320px·390px의 가로 넘침 없음. 운영자 카드의 배지·시간 범위가 한 줄로 유지되는 것을 브라우저의 실제 글자 배치와 캡처로 확인했다.
- `npm run check` 통과: 린트, 타입 검사, 단위·DB 테스트 **433개**, 프로덕션 빌드 완료.
- 로컬 DB의 기존 마이그레이션 33개 적용 상태 확인. 새 마이그레이션 없음.
- 검증 완료 시점에는 로컬 반영 상태였으며, 커밋·푸시·운영 배포는 후속 작업으로 분리했다. 같은 날 사용자 요청으로 main 반영과 운영 배포를 진행한다. 운영 확인은 배포 상태·도메인 연결·상태 API·로그인 진입 경로를 대상으로 하며, 운영 DB에서 테스트 신청이나 금전 기록을 만들지 않는다.

새 연속 경로만 다시 검증하려면, 기존 실행 지침에 따라 **전용 로컬 E2E DB**를 준비하고 `E2E_DATABASE_URL`을 설정한 뒤 아래 명령을 실행한다. 테스트가 전용 DB의 데이터를 초기화하므로 실제 사용자 데이터가 있는 DB를 지정하지 않는다.

```sh
DATABASE_URL="$E2E_DATABASE_URL" DATABASE_URL_UNPOOLED="$E2E_DATABASE_URL" npm run e2e -- tests/e2e/court-mobile-journey.spec.ts
```

실행 캡처는 `test-results/` 아래 생성한다. 운영자 공개 카드 320px·390px, 신청 실패 후 재시도 창, 참가 확정 320px·390px, 환불 완료 화면을 남긴다. 테스트 산출물은 저장소에 커밋하지 않는다.

## 5. 실기기에서 남은 확인

자동 테스트와 별도로, 운영자·참가자 테스트 계정으로 다음을 확인한다.

1. **로그인:** iPhone Safari 또는 Android Chrome에서 카카오 로그인 후 원래 화면으로 돌아오는지 확인한다.
2. **입력:** 연락처·자기소개·입금자명·환불 계좌 입력 시 키보드가 현재 입력과 저장 버튼을 가리지 않는지 확인한다. 키보드를 닫은 뒤 화면 확대와 스크롤 위치도 확인한다.
3. **신청·복귀:** 목록 → 상세 → 신청 창 → 닫기·다시 열기 → 신청 순서로 진행한다. 브라우저 뒤로 가기로 목록과 상세에 돌아오는지 확인한다.
4. **전화·채팅:** 신청 후 전화 버튼이 등록된 번호로 전화 앱을 여는지 확인한다. 참가 확정 후 서로 다른 계정에서 채팅을 주고받는다.
5. **취소·환불:** 표시된 예상 환불액과 입력한 계좌를 확인하고, 운영자 처리 중·완료 후 참가자 화면을 새로 확인한다. 실제 송금 여부는 은행 내역으로 별도 확인한다.

실기기 결과에는 기종·OS·브라우저·진행 단계·화면 증상을 함께 기록한다. 실제 카카오 인증, 전화 앱 전환, OS 키보드와 실송금은 자동 검증 완료 항목으로 표시하지 않는다.
