# 코트 매칭 기본정보 재사용·문의 연락처 화면 설계

2026-10-03 · 기준 `a9f1ad4` · **사용자 승인 후 화면 구현·로컬 검증 완료 · 운영 미반영**

## 1. 목적과 변경한 방향

운영자가 이미 등록한 운영자·코트 정보를 매칭마다 다시 입력하지 않게 하고, 참가자가 필요할 때 실제 담당자에게 연락할 수 있게 한다. 코트 확보와 신청 이후 이용에 대한 불안을 줄이는 MVP 흐름의 개선이다.

사용자는 운영자 가입·코트 등록에서 저장한 정보와 별도 운영자 입력란이 중복되고, 매칭 등록 때마다 입력하는 방식은 과하며, 이용자에게 필요한 것은 대표자 정보보다 문의 가능한 연락처라고 지적했다.

이에 **별도 공개 사업자 정보 입력·재심사·매칭별 확인 절차를 이번 설계에서 제외**한다. 기존 운영자 등록과 코트 기본정보를 재사용하고, 문의 전화번호·연락 가능 시간을 최초 코트 설정에서 한 번 등록하는 방향이다. 매칭 등록에서는 연락처를 읽기 전용으로 보여 주며 변경할 때만 같은 화면 위에 기본정보 설정 창을 연다. 공개 범위 확인도 최초 등록·연락처 변경 시 수행하고 매칭마다 다시 요구하지 않는다.

이전 시안의 신청 전 대표 전화·이메일 공개와 공개 사업자 정보 미등록 경기의 신규 신청 중지 제안은 채택하지 않는다. 앞서 질문한 두 항목은 이번 작업의 승인 대기 조건에서 제외한다. 기존 [03-15](03-15-court-operator-contact.md)의 신청 후 연락처 공개·기존 경기 유지 정책을 따른다.

[수정 시안](previews/court-provider-information.html)은 가상 정보로 구성했다. 기본정보를 수정하면 같은 시안 안의 매칭 등록·참가 상세에 반영되지만 실제 저장·신청·전화 발신은 하지 않는다.

실제 구현은 가입 이후 최초 설정의 진입 동선과 매칭 등록의 요약 표시를 개선하는 범위다. 새 사업자 심사 시스템, 계정 종류·로그인 방식 변경, 추가 DB 모델은 필요하지 않다. 가장 단순한 대안은 현행 운영 홈의 연락처 등록 링크를 유지하는 것이지만 최초 설정 때 함께 안내하면 공개 직전에 뒤늦게 연락처를 입력하는 단계를 줄일 수 있다.

## 3. 화면과 저장 단위

### 최초 운영자·코트 설정

1. 기존 심사를 위해 필요한 운영자 정보와 코트 이름·주소를 등록한다. 심사 입력 자체를 이번 작업에서 삭제하거나 참가자에게 자동 공개하지 않는다.
2. 코트 기본정보 설정에서 문의 전화번호와 연락 가능 시간을 한 번 입력한다. 이미 있으면 기존 값을 보여 준다.
3. 해당 신청자에게 공개되는 조건을 확인하고 저장한다. 계정 인증 공급자의 전화번호나 지도 검색 결과를 임의로 가져오지 않는다.

현재 연락처 저장 API는 Court가 있어야 한다. 최초 설정을 가입 흐름에 연결할 때에는 코트 생성 이후 같은 화면 흐름에서 저장하도록 하며, 존재하지 않는 Court에 연락처를 기록하거나 별도 임시 계정 연락처 모델을 만들지 않는다. 저장 실패 시 재시도할 수 있어야 한다.

### 코트 매칭 등록

- 저장된 코트 이름·주소와 문의 연락처를 자동으로 불러온다.
- 운영자 이름·대표자·사업자번호·주소·전화번호를 다시 입력하는 폼을 두지 않는다.
- 문의 연락처는 전화번호·연락 가능 시간과 작은 `변경` 버튼으로 표시한다. 번호가 유효하면 재확인 체크박스 없이 진행한다.
- `변경`은 기존 연락처 관리 컴포넌트를 재사용한 공통 기본정보 설정 창을 연다. 해당 코트의 모든 경기에서 사용하는 연락처라는 점을 변경 화면에 안내한다. 경기 한 개만 바뀌는 것으로 오해시키지 않는다.
- 설정 창을 열고 닫아도 매칭 폼을 유지하여 작성 중인 날짜·시간·인원·비용을 보존한다. 설정 창을 열 때 현재 코트 연락처를 다시 읽고, 저장·최신 정보 재조회 결과를 원래 화면에도 반영한다. 연락처 화면의 저장 실패가 매칭 초안 유실로 이어져서는 안 된다.
- 운영자는 해당 경기의 일시·코트 번호·게임 유형·정원·참가비·제공 항목 등 경기별 조건만 입력한다.
- 연락처가 없으면 초안 저장은 허용하고 새 공개 전에 최초 등록을 안내한다. 기존 공개 경기의 새 신청은 임의로 중단하지 않는다.

### 참가자 상세

- 신청 전에는 일시·장소·참가 조건·비용 등으로 판단하게 한다. 대표자 정보 카드나 별도의 사업자 연락처 입력·표시를 추가하지 않는다.
- 신청 후에는 `운영자 문의`에 **전화번호 · 연락 가능 시간 · 전화하기**만 간결하게 표시한다.
- 기존 정책처럼 접수 후 종료 24시간까지, 철회·거절·취소 등은 미처리 입금·환불이 있는 동안에만 공개한다. 종료 24시간 뒤에도 미처리 거래가 남으면 해결까지 유지한다.
- 운영자 공개 중단·탈퇴 등 연락 불가 상태와 기존 문의 경로는 현행 처리대로 유지한다. 네이버 등에서 추정한 번호를 대체 표시하지 않는다.
- 목록 카드와 신청 안내 기록에 전화번호를 추가하지 않는다. 신청 안내 v2를 유지한다.

## 4. 개인정보·기존 정책과의 정합성

운영자 심사 정보, 코트의 공통 문의 연락처, 경기별 조건은 목적과 저장 단위가 다르다. 별도 연락처 입력이 필요한 것은 미등록·변경 때이며 경기 등록을 반복한다는 이유로 같은 정보를 다시 수집하지 않는다.

현행 `03-1`의 심사 자료 비공개, 정본 `03-2` 및 `03-15`의 연락처 공개 권한을 바꾸지 않는다. 새 공개 제공자 모델이나 기존 경기의 신청 중지 조건도 추가하지 않는다. 일반 매칭의 개인 모집자에게 별도 사업자 정보를 받지 않는다.

### 공개 제공자 정보의 후속 검토

입력 부담을 줄이는 결정과 실제 거래 제공자의 필요한 고지 항목 검토는 구분한다. 이번 단순화로 법적 고지가 연락처 하나면 충분하다고 확정하지 않는다. 앞선 공식 원문 확인 근거는 아래에 남기되, 필요한 고지가 확정되면 **이미 등록된 정보의 재사용과 최초 설정에서의 최소 보완**으로 해결한다. 경기별 재입력 폼으로 되돌리지 않는다. 비공개 심사 정보를 승인 없이 자동 공개하지 않는다.

- [전자상거래법 제13조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0013&lsiSeq=282793&urlMode=lsScJoRltInfoR)

## 5. 구현 내용과 검증 기준

1. 운영자 최초 설정에 기존 연락처 관리 경로를 연결하고 코트 생성 전후의 상태를 구분한다.
2. 매칭 등록에서 저장된 정보의 요약·수정·복귀를 제공한다. 운영자가 해당 Court의 소유자인지 서버에서 확인한다.
3. 값 누락·저장 실패·동시 수정의 버전 충돌, 번호 공개 중단과 새 공개의 동시 처리, 신청 전·다른 회원의 번호 비노출을 유지한다.
4. 최초 등록 한 번으로 두 번째 매칭도 재입력 없이 등록되는지, 변경한 번호가 기존·신규 참가 상세에 반영되는지, 설정을 오가도 매칭 초안이 유지되는지 검증한다.
5. 실제 앱을 수정한 뒤 관련 테스트·타입 검사·린트·빌드와 모바일 흐름을 검증한다.

사용자가 수정 시안에 동의하여 실제 화면 구현을 진행했다.

- 운영자 심사 후 초안 준비 및 운영 홈에서 `코트 기본정보 설정하기`로 진입한다. 기존 Court가 없는 경우 신청 당시 이름·주소를 표시하고 지역만 선택한다. 코트를 만든 뒤 연락처 설정 창을 바로 연다.
- 기존 Court가 있으면 `내 코트`·`문의 연락처` 요약을 보여 준다. 연락처 등록·수정은 기존 `/partner/contact`와 같은 컴포넌트·API·검증을 사용한다.
- 특정 Court ID의 연락처를 다시 조회하며, 저장·공개 중단 결과를 원래 매칭 화면에도 반영한다. 매칭 폼을 이동·재초기화하지 않아 미완성 입력도 보존한다. 브라우저 새로고침이나 다른 페이지로 이동한 뒤의 초안 복구까지 제공하는 기능은 아니다.
- 최초 코트 생성 성공 후 연락처 저장이 실패해도 생성한 코트를 유지해 재시도한다. 연락처 없이 시간 초안을 저장하는 기존 경로도 유지한다.
- 저장 중 설정 창 닫기를 막고, 동시 변경은 기존 버전 충돌·최신 정보 재조회로 처리한다. 공개 동의는 번호 등록·변경 때만 받는다.

API·데이터 모델·개인정보 공개 조건·신청 안내 버전은 변경하지 않는다. 운영 DB·배포·크론도 이번 작업에서 변경하지 않는다.

## 6. 시안 검증

2026-10-03 수정 시안의 매칭 등록·신청 전·신청 후·기본정보 관리 네 상태를 새로 검증했다. 매칭 등록에 기본정보 재입력란이 없는지, 현재 번호 불러오기·수정 취소·필수값과 공개 동의 검증·수정 후 공통 표시 갱신이 동작하는지 확인했다. 신청 전 번호 비표시, 신청 후 수정한 연락처 표시, 확인 창 및 전화 미리보기 안내도 확인했다.

320px·390px·1040px에서 가로 넘침이 없었고 페이지 실행 오류가 없었다. 모바일 캡처로 정렬을 확인했으며 사용자에게 열려 있는 시안 탭도 최신 내용으로 갱신했다. 실제 서비스의 가입 저장·권한·API 흐름을 변경하거나 검증한 결과는 아니며, 애플리케이션 전체 테스트와 빌드는 문서·정적 시안만 변경한 이번 작업에서 다시 실행하지 않았다.


## 7. 실제 앱 검증 결과 (2026-10-03)
