# 개인정보 저장·열람·삭제 현황 점검

작성일: 2026-10-06 · 검토 기준: `main`의 `9d4227402e97daf6b22bbd6ddc4fb12a7add1763`

## 1. 이번 작업의 범위

사용자가 선택한 첫 작업인 **현재 보유 정보, 조회 권한, 삭제 시점의 목록화**를 수행했다. 아래 내용은 저장소 코드·스키마·문서를 대조한 결과이며 새 보관 정책이 아니다. 개인정보 원문이나 운영 DB를 조회하지 않았고, 실제 삭제·권한 변경·배포·크론 설정 변경도 하지 않았다.

클라우드 백업·로그의 실제 보관 설정, 저장소의 실제 잔존 파일, 현재 카카오 동의 항목은 이번 확인 범위 밖이다. 법적 보존 의무나 연수를 확정하지 않는다. 코드에 삭제 절차가 없다는 사실과 법적으로 보관할 수 있다는 판단은 별개다.

관련 기준:

- [탈퇴 후 거래 연속성](03-10-account-transaction-continuity.md): 본인 거래 정리를 유지하지만 전체 프로필·채팅·계좌의 무기한 보관을 승인한 것은 아님.
- [운영자 연락처](03-15-court-operator-contact.md), [기본정보 재사용](03-16-court-provider-information-design.md): 현재 연락처의 조건부 공개, 신청 안내에 전화번호를 복사하지 않음.
- [채팅 설계](08-in-app-match-chat-design.md): 메시지·신고의 최종 보관·파기 기준은 공개 출시 전 미확정 사항.
- [개인정보 안내 소스](../src/app/privacy/page.tsx): 2026-10-03 안내에도 보관 기간·파기 절차가 미정으로 남아 있음.
- [인수인계 §0](03-3-court-match-work-handoff.md): 크론 작업은 계속 보류. 운영자 주최 코트 매칭의 정본은 03-2이며, 03-1의 폐기된 세션 설계는 적용하지 않음.

## 2. 핵심 결과

1. **열람 차단과 실제 삭제가 분리되어 있다.** 연락처 공개 기한, 탈퇴 상태, 채팅 읽기 전용 전환이 저장 데이터 삭제를 뜻하지 않는다.
2. **계좌 원문이 여러 곳에 있다.** 운영자 기본 계좌는 매칭별로, 참가자 환불 계좌는 송금 시도별로 복사된다. 완료 후 원문 삭제·마스킹 기한은 없다.
3. **탈퇴 시 사진 참조는 지우지만 계정·프로필·신청·문의·거래 정보는 남는다.** 환불이 없는 계정도 같은 소프트 탈퇴 처리를 한다. 정보별 보존 목적·종료 조건이 필요하다.
4. **해결된 문의와 채팅 원문의 파기 절차가 없다.** 내부 담당자의 문의 목록 조회는 업무 배정 여부보다 넓다.
5. **파일 정리 기능에도 보완점이 있다.** 프로필 사진 삭제 실패의 재시도 기록, 중단된 정리 작업 회수, 증빙 메타데이터 정리 여부를 확인해야 한다.
6. **DB 밖의 복사본도 대상이다.** 로그인 쿠키·브라우저 이미지 캐시·로컬 백업·서비스 로그를 별도로 다뤄야 한다.

아래에서 ‘삭제 미구현’은 검토한 제품 실행 경로에 보관 종료 후 삭제·익명화가 없다는 뜻이다. 운영 데이터가 유출됐거나 외부 저장소에 영구 보관된다는 뜻은 아니다.

## 3. 저장 정보와 조회 범위

조회 권한은 서비스 API 기준이다. DB·배포·객체 저장소 관리자의 직접 접근 권한은 별도 운영 설정 점검이 필요하다.

### 3.4 사진·채팅·운영자 심사

모든 기간은 코드에 있는 정리 **대상 선정 기준**이다. 그 시각에 실제 파일 삭제가 완료됐다는 보장은 아니며, 기존 정리 작업의 실행·실패 여부를 이번에 확인하지 않았다.

## 4. 놓치기 쉬운 복사본과 완료 조건

### 4.1 계좌 한 곳만 지우면 완료가 아니다

```text
운영자 기본 계좌 Court
  └─ 경기 공개 시 → Match의 정산 계좌

참가자 환불 계좌 MatchApplication
  └─ 송금 시작 시마다 → CourtRefundAttempt의 은행·계좌·예금주

계좌·전화 등을 자유 입력에 직접 기재한 경우
  └─ 문의 / 거래 메모 / 신청 메시지 / 채팅 / 사진에도 원문이 남을 가능성

위 데이터가 저장된 시점의 DB·파일 백업
  └─ 원본 삭제 뒤에도 별도 복사본으로 남을 수 있음
```

거래 금액·처리 시각·확인 근거를 보존하는 것과 계좌번호 전체를 계속 제공하는 것은 분리해서 결정해야 한다. 과거 송금 계좌를 현재 계좌로 덮어쓰면 대조 근거가 사라지므로, 보존·마스킹·삭제를 별도 단계로 설계할 필요가 있다.

### 4.2 환불 완료만으로 모든 업무가 끝났다고 판단할 수 없다

현재 구현에는 늦은 입금, 송금 확인 필요(`REVIEW`), 처리 중(`PROCESSING`), 문의 재개가 존재한다. `refundCompletedAt` 하나만 보고 계정·인증 연결·계좌를 일괄 삭제하면 남은 업무를 처리하지 못할 수 있다.

반대로 거래 하나가 미해결이라고 전체 프로필·모든 과거 문의·사진을 함께 보존할 필요가 있다고 단정할 수 없다. 다음 정책 단위에서 **거래별 예외와 정보별 보존 범위**를 나눠야 한다.

정책 선택에 따른 차이는 다음과 같다. **권장 방향**은 거래 근거와 민감 원문을 분리하고, 미해결 거래에 한정해 필요한 정보만 예외로 남기는 방식이다. 대안인 계정 전체 즉시 삭제는 늦은 입금·환불 문의를 막을 수 있고, 전체 기록 장기 보관은 불필요한 프로필·계좌·대화까지 남긴다. 권장 방향을 채택하면 사용자에게 처리 중인 거래 접근을 유지하면서 불필요한 원문을 줄일 수 있으나, 항목별 만료·예외·삭제 결과를 표현하는 데이터 모델과 권한 검증이 필요하다. 이번에는 어느 안도 실제 적용하지 않았다.

## 6. 다음 작업에 넘길 결정 목록

다음 단위는 **탈퇴·거래 종료 후 무엇을 남길지 정책표를 확정하는 것**이다. 다음 순서가 적절하다.

1. **처리 중 거래 예외:** 미확인 입금, 미지급 환불, 송금 처리 중·재확인, 미해결 문의를 각각 정의하고 어떤 정보만 유지할지 정한다. 거래별 해결·재개 조건도 포함한다.
2. **거래 완료 뒤 원문:** 계좌·입금자명·문의 원문을 거래 금액·시각·처리 근거와 분리한다. 원문 열람 종료, 마스킹, 실제 삭제의 시작점과 기간을 정한다.
3. **탈퇴 프로필·로그인:** 현재 프로필·신청 스냅샷·닉네임을 언제 삭제/대체할지, 제한 거래 로그인에 필요한 카카오 연결과 세션 필드를 얼마나 유지할지 정한다.
4. **채팅·신고·증빙:** 일반 대화와 신고 보존 예외를 분리하고, 기존 증빙 24시간/30일 정리와 남길 최소 삭제 이력을 맞춘다.
5. **삭제 확인:** DB의 모든 복사본, Blob, 로컬·클라우드 백업, 로그까지 대상별 책임·결과 확인·실패 재처리를 정한다.

정책과 적용 범위가 정해진 뒤 관련 문서·API·스키마·테스트를 하나의 검토 가능한 단위로 수정한다. **크론 주기 변경·외부 스케줄러·유료 전환은 사용자의 재개 요청 전까지 계속 보류한다.**

## 7. 검증 범위와 한계

- `prisma/schema.prisma`, 인증·탈퇴·프로필·매칭·금전·문의·인계·채팅·파일 서비스, 관련 API, `vercel.json`, 제품 문서를 정적으로 대조했다.
- 삭제·익명화·만료·캐시·로그·브라우저 영속 저장 경로를 검색하고 실제 삭제·조회 함수까지 읽었다. 테스트용 seed의 삭제를 제품 파기 절차로 계산하지 않았다.
- 기존 백업은 파일 존재만 확인했다. 운영 DB 행, 회원 사진·문의·계좌 원문, 세션 쿠키, 비밀 환경 변수는 읽지 않았다.
- 이번 변경은 이 점검 문서 한 파일뿐이다. 제품 코드·DB·크론을 바꾸지 않아 앱 테스트·타입 검사·린트·빌드·모바일 E2E는 새로 실행하지 않았다. 이 결과를 운영 환경의 실삭제 성공 또는 법적 적합성 검증으로 표현하지 않는다.
- 문서의 로컬 링크 대상 존재 여부와 문서 한 파일만 추가된 변경 범위를 확인했다. 미확정 사항은 §5·§6에 남겼다.
