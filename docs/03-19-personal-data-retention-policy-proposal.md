# 탈퇴·거래 종료 후 개인정보 처리 정책안

작성일: 2026-10-06 · 후속 구현: 2026-10-09 · 현황 기준: `9d42274` · **계좌 원문 정리 승인, 읽기 전용 점검 구현, 실제 파기·운영 미적용. 채팅 기준 선택 대기**

## 1. 목적과 이번 작업의 완료 범위

[03-18 현황 점검](03-18-personal-data-retention-inventory.md)에 이어, 거래를 처리할 수 있는 최소 정보와 목적이 끝난 개인정보를 구분한다. 탈퇴 때문에 환불·문의가 막히거나, 반대로 미해결 거래 하나 때문에 전체 프로필과 대화가 계속 남는 문제를 줄이기 위한 정책안이다.

이번 결과물은 정보별 처리 기 준, 거래 종료 판정, 예외·권한·삭제 확인 방법, 후속 구현 순서다. 공개 개인정보 처리방침이나 기존 사용자 데이터는 바꾸지 않는다. 확정된 사용자 선택은 §8에 기록하며, 그 외 ‘권장’과 예시 기간은 사용자 결정이나 법률 적용 확인을 대신하지 않는다.

Core MVP의 신청·참가·문의·거래 정리를 마무리하는 범위이며 새 결제 방식·고객센터·외부 서비스는 추가하지 않는다. 단순히 모든 정보를 즉시 지우면 거래 확인이 끊기고, 계정 상태만 바꾸면 불필요한 정보가 남으므로 항목별 처리가 필요하다. 구현은 한꺼번에 계정 전체를 지우는 기능보다 커지지만, 기존 DB·권한·금전 처리 구조를 재사용하는 작은 단위로 나눈다.

## 2. 법령 기준과 제품 결정의 구분

2026-10-06 국가법령정보센터에서 아래 조문을 확인했다. 실제 판매·중개 역할, 처리 항목, 보존 시작점은 운영 사실에 맞춰 확인해야 한다. 개인 운영이라는 사실이나 앱에서 직접 결제하지 않는다는 이유만으로 적용 여부를 단정하지 않는다.

위 법정 기간과 아래 채팅 30일 등의 **제품 권장 기간은 다른 성격**이다. 계좌 끝 네 자리나 내부 사용자 ID도 다른 기록과 연결된다면 개인정보일 수 있으므로 ‘완전 익명화’라고 표시하지 않는다. 구체적인 법 적용과 보존 범위는 전문 검토로 확인할 항목을 남긴다.

## 3. 권장 처리 원칙

1. **탈퇴 프로필 정리와 남은 거래 정리를 분리한다.** 개인 프로필을 계속 보관하지 않아도 거래 ID·금액·처리 근거로 환불 업무를 이어갈 수 있게 한다.
2. **계좌 원문은 실제 대조·송금에 필요한 동안만 유지한다.** 해당 업무가 끝나면 전체 번호·예금주를 정리하고 필요한 거래 근거를 분리한다. 미처리 건에 필요한 원문은 해당 건만 예외로 남긴다.
3. **일반 열람 종료, 제한 보관, 실제 파기를 구분한다.** 읽기 전용·숨김·소프트 탈퇴를 삭제 완료로 표시하지 않는다.
4. **보존 예외를 기록 단위로 지정한다.** ‘분쟁 가능성이 있다’는 추상적 이유로 계정 전체에 종료일 없는 예외를 붙이지 않는다.
5. **같은 정보의 모든 복사본을 함께 처리한다.** 현재 계좌와 과거 송금 계좌, 본문·첨부, DB와 객체 저장소·백업을 구분해서 확인한다.
6. **파기 후 늦은 입금은 새 업무로 처리한다.** 삭제한 원문을 백업에서 복원해 재사용하지 않고 필요한 정보만 다시 받는다. 과거 신청 자리를 복구하지 않는다.

## 4. ‘업무가 끝났다’의 기준

### 4.1 신청 상태와 보관 상태는 다르다

`CANCELLED`, `WITHDRAWN`, `EXPIRED_UNPAID`, `COMPLETED` 같은 상태만으로 금융 정보 파기 여부를 결정하지 않는다. `refundCompletedAt`도 단독 완료 조건이 아니다.

| 판단할 상황 | 유지가 필요한 정보 | 종료 조건·범위 |
| --- | --- | --- |
| 아직 이용 전·이용 중인 참가 | 신청·제공 조건, 참가 자리, 필요한 승인 정보, 입금 처리 정보 | 이용 또는 참가 취소가 끝나고 남은 금전 업무 확인. 코트 일정 종료와 탈퇴 요청을 구분 |
| 입금 알림이 있으나 대조되지 않음 | 해당 신청의 입금자명·코드·금액·알림, 대조에 필요한 수령 계좌 정보 | 알림 이후 은행 대조 완료. 시간 경과만으로 미입금을 확정하지 않음 |
| 반환 잔액이 있음 | 해당 반환 건의 실제 수령·반환 계산·송금 대상 계좌·처리 근거 | 실제 지급 또는 정정이 반영되어 잔액이 0이고 송금 재확인도 없음 |
| 송금 `PROCESSING` 또는 `REVIEW` | 송금 시도에 고정한 계좌·금액·처리 이력 | 은행 결과를 대조해 `PAID`·`FAILED` 등을 확정. 0원 표시여도 처리 중 원문 삭제 금지 |
| 과다 반환·기록 충돌 | 충돌하는 입금·반환 기록과 필요한 증거 | 담당자가 대조 결과·정정 근거를 기록. 화면에서 금액만 0으로 바꿔 종료하지 않음 |
| 관련 문의·분쟁이 진행 중 | 그 사건에 필요한 메시지·증거·거래 연결 | 담당 처리와 관련 금전 업무 종료. 문의 하나가 다른 경기 전체 보관을 연장하지 않음 |
| 법적 보존 필요 | 적용 법령상 최소 거래·분쟁 기록과 식별 정보 | 정해진 기산점·기간 종료. 일반 서비스 조회와 분리 |

현재 코드는 `receivedAmountKrw: null`을 미대조 가능 상태로 표시하지만, 이것만으로 **모든 미입금 신청을 무기한 보존**해서는 안 된다. 신청 단계에서 계좌가 공개됐는지, 입금 알림·실제 수령·진행 중 문의가 있는지 구분해야 한다. 특히 계좌 안내 전 거절된 무입금 신청과, 계좌 안내 뒤 만료된 신청을 같은 미대조 건으로 취급하지 않는다.

계좌 안내 뒤 종료된 신청은 해당 입금 코드·안내 계좌에 대한 마지막 은행 대조 근거를 남기는 안을 권장한다. 반복 클릭을 요구하는 별도 폼을 추가하기보다 기존 입금 확인·환불 결과 처리에서 대조 확인을 함께 기록한다. 완전 자동 판단이 가능한 건과 실제 통장 확인이 필요한 건을 분리한다.

### 4.2 구현에 필요한 최소 판정 정보

기존 금전 계산 `courtMoneySummary`를 재사용하되, 금융 파기 후보를 확정하기 전에 다음을 확인한다.

- 이용·신청 업무가 종료됐는지.
- 실제 입금 대조가 필요한 건이면 언제, 어느 입금 알림·수령 기록 버전까지 대조했는지.
- 미지급액·송금 처리 중 금액·재확인 필요 여부가 모두 해소됐는지.
- 해당 항목을 보존해야 하는 진행 중 문의·사건 또는 법정 보존 근거가 있는지.
- 원문 제거 이후 다시 대조가 필요하면 어떤 최소 식별 정보로 재개할 수 있는지.

`depositClaimedAt` 뒤에 기록 하나가 있다는 사실만으로 새로운 파기 권한을 만들지 않는다. 연락처 공개에 쓰던 판정은 연락 안내를 위한 것으로, 은행 대조 완료 증빙과 동일하다고 가정하지 않는다.

또한 현재 `courtMoneySummary`는 과거 데이터에서 실제 수령액이 없으면 `confirmedAt`과 참가비로 수령액을 추정한다. 화면 호환용 계산을 실제 은행 대조의 증거로 승격하지 않는다. 과거 환불 완료 금액 역시 새 대조 시각·담당자·계좌 확인 근거를 자동 생성하는 근거가 아니다.

종료 시각·대조 버전·예외와 파기 상태는 실제 업무 상태 변경과 같은 트랜잭션에서 확인해야 한다. 문의 재개·늦은 입금·송금 시작과 동시에 파기 후보를 처리하더라도, 먼저 확정된 업무와 충돌하지 않게 기존 거래 잠금 순서를 유지한다.

## 5. 정보별 정책안

‘즉시 정리’는 불필요해진 원문의 서비스 열람을 차단하고 DB 삭제를 실행하는 방향을 뜻한다. 외부 객체 삭제가 실패하면 성공으로 표시하지 않고 실패 건을 남긴다. 임의의 30일 대기 기간을 붙여 즉시 삭제라고 안내하지 않는다.

| 정보 | 권장 처리 시점·기간 | 남겨야 하는 예외·최소 기록 | 사용자 경험·구현 영향 |
| --- | --- | --- | --- |
| 현재 테니스 프로필·프로필 사진 | 탈퇴 시 현재 프로필·선호 플레이 삭제, 사진 참조 차단 및 객체 삭제. 닉네임의 일반 표시도 탈퇴 회원 표시로 전환 | 진행 거래 식별은 별도 거래 참조로 유지. 사건에 필요한 과거 신청 정보만 개별 예외 | 탈퇴 후 추천·프로필 복원 없음. 일반 매칭·채팅의 과거 표시가 빈 프로필을 처리하도록 검증 필요 |
| 카카오 인증 연결 | 미해결 업무 또는 보존 중인 본인 거래 열람에 필요한 최소 연결만 분리 유지. 마지막 필요 기록의 기간 종료 후 삭제 | 거래 조회용 연결과 일반 서비스 가입 상태 분리. 로그인 쿠키에는 불필요한 이름·이메일·사진을 제거하는 방향 | 단순히 환불 잔액 0원이 됐다고 열람 인증을 끊지 않음. 마지막 연결 삭제 후 재로그인·재가입 정책은 별도 결정 전 변경하지 않음 |
| 신청 프로필·자기소개 | 모집·참여 조율 목적 종료 시 일반 열람 종료 및 필요 없는 원문 정리 | 다툼의 근거가 된 구체 항목만 별도 사건 기록. 자리·성별 확인 근거는 실제 거래 필요 범위로 분리 | 신청 당시 안내·금액 증거를 지우는 작업과 구분. 과거 프로필 전체를 법정 거래 기록으로 일괄 보존하지 않음 |

## 6. 열람 권한과 보존 예외

### 6.1 담당 배정 전후

문의·인계 대기 목록은 접수 시각, 상태, 경기·신청 참조, 배정 여부, 필요한 분류 정도로 제한하는 안을 권장한다. 문의 원문·상세 거래 사유는 배정된 활성 담당자에게만 제공한다. 권한이 종료된 담당자는 다른 활성 담당자에게 업무를 넘기며, 본인 관련 거래를 스스로 처리하지 않는다.

해당 운영자는 이미 구현된 별도 대조 요청 내용만 열람한다. 참가자의 다른 문의·다른 경기·신고 원문을 같이 공개하지 않는다. 법정 보존 상태로 옮긴 기록은 일반 운영 화면·추천·매칭 프로필 조회에서 제외하고, 당사자의 기록 열람 및 사유가 있는 제한된 담당 업무에 사용한다.

1인 운영에서도 이 구분은 유지할 수 있다. 본인 관련 사건의 대체 담당자가 없으면 권한 검사를 풀지 않고 별도 처리 경로를 먼저 정한다. 실제 외부 문의 채널은 여전히 미정이다.

### 6.2 예외를 남길 때 필요한 항목

최소한 사건 ID, 대상 거래·데이터 항목, 사유·근거, 담당자, 설정 시각, 다음 검토 시각, 해제 조건을 기록한다. 만료 시각이 정해진 법적 보존과 조사 종료 때까지 필요한 증거 보존을 구분한다.

- 권장 운영 방식: 열린 예외를 기존 업무 확인 과정에서 주 1회 재검토. 이는 자동화 설정이나 사용자의 실응대 시간 확정이 아니다.
- 단순히 ‘환불 가능성 있음’, ‘불만 생길 수 있음’은 전체 데이터 예외 사유가 될 수 없다.
- 문의 재개는 해당 문의·새 증거에만 반영한다. 모든 과거 기록의 보관 시계를 다시 시작하지 않는다.
- 이미 파기한 원문은 복원하지 않는다. 새로 확보한 자료의 수집 목적·시점·기한을 기록한다.

## 7. 삭제 실행과 검증 조건

### 7.1 삭제 완료의 의미

1. 일반 응답·다운로드에서 대상 원문의 열람을 차단한다.
2. DB의 대상 필드와 복사본을 정리한다. 삭제 대상 사진은 참조를 잃기 전에 재시도 가능한 최소 작업 정보를 남긴다.
3. 외부 객체 삭제의 성공·실패를 확인한다. 실패를 삼키거나 `DELETED`로 표시하지 않는다.
4. 정리 중 프로세스가 멈춘 항목을 다시 처리할 수 있게 한다. 재시도 때 원문을 로그에 복사하지 않는다.
5. 완료 후 불필요한 객체 URL·소유자 연결을 삭제한다. 삭제 감사 기록도 필요한 최소 항목만 남긴다.
6. 백업·캐시의 별도 잔존 범위를 관리한다. 백업을 복원하면 서비스 재개 전에 파기 완료 이력을 재적용해 삭제한 정보가 다시 노출되지 않게 검증한다.

백업에 삭제 대상이 남아 있는 동안 ‘모든 복사본 파기 완료’로 표시하지 않는다. 클라우드의 실제 복구 창·백업 주기·파일 파기 지원을 확인한 뒤 실행 가능한 설명을 개인정보 처리방침에 반영한다.

### 7.2 크론 보류와 운영 가능성

사용자의 기존 결정대로 `vercel.json` 주기 변경, 새 외부 스케줄러와 유료 전환을 하지 않는다. 새 기한 기반 파기를 자동 실행한다고 약속하지 않는다.

후속 구현은 우선 **탈퇴·연락처 중단·금전 대조 완료처럼 실제 요청이 발생하는 시점의 처리**와 삭제 실패를 남기는 절차부터 검토한다. 채팅 기한 만료처럼 접속이 없어도 처리해야 하는 항목은 별도 실행 담당·방법·확인 절차가 필요하다. 요청 시 보정만으로 실제 파일의 제시간 파기까지 보장하지 않는다. 크론 보류를 개인정보 무기한 보관의 근거로 사용하지 않는다.

## 8. 사용자 결정 항목과 대안

이번에 확인할 핵심은 두 가지다. 다른 항목의 권장안까지 자동 승인된 것으로 간주하지 않는다.

### Q1. 대조가 끝난 계좌 원문

**2026-10-06 사용자 결정: ‘대조 완료 후 원문 정리 (권장)’ 선택.** 별도 보존 사유가 없는 계좌 전체번호·예금주·입금자명을 정리하고, 필요한 금액·은행·끝 네 자리·처리 시각은 남기는 방향을 확정했다. 미해결·분쟁 건의 필요한 원문 보존과 늦은 환불 시 계좌 재입력도 질문에 포함된 조건이다. 아직 코드·DB에 적용하지 않았다.

- **권장:** 거래 대조·반환이 끝나고 별도 보존 사유가 없는 전체 계좌번호·예금주·입금자명은 정리한다. 필요한 금액·은행·끝 네 자리·처리 시각 등은 분리 보관한다. 미해결·분쟁 건에 필요한 원문만 예외로 남긴다.
- **대안:** 완료 후 추가 대조가 실제로 필요한 업무를 먼저 정하고, 그 업무에 한정한 짧은 확인 기간을 추가한다. 구체 목적 없이 30일·90일을 일괄 부여하지 않는다.
- **차이:** 권장안은 불필요한 원문 보유를 줄이지만 늦은 환불 때 계좌 재입력이 필요하다. 추가 확인 기간안은 재입력을 줄이는 대신 필요한 이유·종료일·공개 범위 관리가 추가된다.
- **구현:** 파기 여부·대조 버전, 전체 번호와 거래용 표시 정보 분리, 각 송금 시도 복사본 정리, 계좌 재수집 화면과 검증 필요. 구체 법정 보존 범위 확인 후 적용한다.

### Q2. 일반 채팅의 열람·파기 시점

- **권장:** 정상 경기는 `endsAt + 24시간`부터 읽기 전용, `endsAt + 30일`에 일반 열람 종료 및 원문·사진 파기. 전체 취소 경기는 취소 즉시 읽기 전용, `cancelledAt + 30일`에 동일 처리. 신고·분쟁 예외는 필요한 증거만 분리한다.
- **대안:** 읽기 전용 전환은 같고 열람·파기 기한을 종료·취소 후 7일로 단축한다.
- **차이:** 30일은 경기 뒤 정산 확인·관련 문의를 위해 대화를 다시 확인할 여유를 주며, 7일은 보유량을 줄이는 대신 기록 확인 기간이 짧다. 두 기간 모두 법정 기간이 아닌 제품 제안이다.
- **구현:** 보관 기한 표시, 서버에서 만료 시 직접 열람 차단, 사진·미확인 수·방 목록을 함께 처리, 사건 증거 분리, 실제 기한별 삭제 실행 체계 필요. 기존 §3.2와 §4.2의 표현 충돌을 결정한 안으로 정리한다.

Q1은 위 선택으로 확정했으며 Q2는 **사용자 선택 대기**다. 이 문서는 [AGENTS.md](../AGENTS.md) §13의 미확정 정책 처리 원칙에 따라 권장안·대안·사용자 경험·구현 영향을 제시한 것이다. Q1의 선택을 탈퇴 프로필·일반 문의·인증 연결 등 다른 미확정 항목의 일괄 승인으로 해석하지 않는다.

## 9. 후속 구현 순서와 완료 기준

1. Q1·Q2 결정 내용을 기록하고 §5의 나머지 권장안·법 적용 미확정 항목을 구분한다. 공개용 안내는 실제 수행 가능한 범위가 확인된 뒤 갱신한다.
2. 최초 구현은 **원문을 지우지 않는 읽기 전용 파기 후보 판정**을 권장한다. 미해결 사유·항목·기간 시작점만 반환하고 실제 값은 출력하지 않는다. 미확정·과거 데이터에는 삭제 후보를 억지로 만들지 않고 필요한 근거를 표시한다.
3. 거래 대조 완료·신고 예외·단계별 파기 표시와 권한을 설계한다. DB 연결·버전·삭제 동시성을 로컬 픽스처로 검증한 뒤 실제 삭제 경로를 별도 단위로 구현한다.
4. 과거 데이터는 소급 동의나 존재하지 않는 대조 시각을 생성하지 않는다. 건수·사유 위주의 모의 실행 결과를 확인한 뒤 적용 범위를 정한다.
5. 운영 적용 전에 필요한 DB·파일 변경, 복구 시 재파기, 기존 정책의 변경 안내와 권리 행사 경로를 확인한다. 기존 백업을 추가로 무기한 복제하는 방식으로 삭제 검증을 하지 않는다.

필수 검증 사례:

- 무거래 탈퇴: 일반 프로필 정리와 다른 이용자 화면의 안전한 과거 표시.
- 미확인 입금·환불 잔액·`PROCESSING`·`REVIEW`·과다 지급 중 하나라도 있으면 해당 원문 파기 중단.
- 계좌 공개 전 무입금 거절과 계좌 공개 후 미대조 만료를 구분.
- 정상 종료·무환불 취소·전액/부분 반환·초과/중복 입금 반환 각각의 대조 완료 판정.
- `confirmedAt`에서 수령액을 추정한 과거 건은 실제 대조 완료로 자동 전환하지 않음.
- 환불 계좌 변경 뒤 모든 과거 시도 복사본 처리. 이미 마스킹된 번호를 송금 계좌로 사용하지 않음.
- 계좌·메모 원문을 정리해도 거래 ID·버전·요청 중복 방지 기록은 필요한 기간 유지하며, 같은 송금 요청을 재전송해 중복 처리되지 않음.
- 문의 재개·늦은 입금과 삭제 동시 요청. 과거 자리 복구·이미 파기된 원문 복구 없음.
- 같은 Court의 다른 활성 경기 연락처·기본 계좌를 잘못 삭제하지 않음.
- 같은 회원의 다른 거래·다른 방이 사건 하나로 전체 보존되지 않음.
- 배정 전 내부 담당자의 원문 차단, 배정·재배정·권한 상실, 본인 사건 처리 차단.
- 채팅 종료·취소 후 24시간/선택 기한 경계, 숨긴 메시지·사진·미전송 업로드·신고 증거 각각 확인.
- Blob 삭제 실패·프로세스 중단·중복 실행·백업 복원 이후의 재노출 방지.
- 새 회원/탈퇴 회원/다른 회원의 거래 열람, 로그인 불가 시 권리 행사 경로의 실제 운영 가능성.

## 10. 2026-10-06 정책안 작성 당시 검증 결과

이번에는 법령 원문과 기존 금전·탈퇴·문의·연락처 판정 코드를 대조해 정책안을 작성했다. 새 기간·권한·파기 로직은 구현하거나 배포하지 않았다. 앱 코드 변경이 없어 앱 테스트·타입·린트·빌드는 실행하지 않았다. 문서의 로컬 링크 대상과 문서만 추가된 변경 범위를 확인했다.

기존 [03-18](03-18-personal-data-retention-inventory.md)은 현황 보고서로 보존한다. 본 정책안과 현행 동작을 혼동하지 않도록 최종 결정·구현·운영 적용 시점을 각각 기록한다.

## 11. 2026-10-09 후속 구현 범위: 금융 원문 보존 점검

사용자의 ‘이어서 진행’에 따라 §9의 첫 구현을 진행한다. 별도 삭제 API·화면·일정 작업을 추가하기 전에, 기존 코트 매칭 기록에서 원문 보유 건수와 정리를 보류할 사유를 읽기 전용으로 집계한다. 개인정보를 계속 보관해야 하는 거래와 검토 가능한 거래를 구분하기 위한 내부 점검 도구이며, 기존 입금·환불 처리는 변경하지 않는다.

- 대상: `PARTNER_COURT` 신청의 입금자명·현재 환불 계좌 원문, 과거 환불 시도의 계좌 복사본, 매칭별 입금 계좌 원문. `Court` 공용 기본 계좌·연락처, 문의·메모 본문, 일반 매칭·채팅은 이번 판정에서 제외한다.
- 입력: 원문 대신 **존재 여부**, 금전 상태·시각·필요한 관계만 조회한다. 출력에는 이름·계좌번호·끝 네 자리·개별 금액·사용자/신청/매칭 ID를 포함하지 않고 항목별 건수·고정된 사유만 남긴다.
- 판정: 미해결 업무가 확인되면 `RETAIN`, 알려진 업무가 끝났지만 대조 완료·법정 보존 검토 등의 근거가 부족하면 `REVIEW_REQUIRED`. 현 스키마에는 최종 대조·원문별 보존 예외 판정이 없으므로 **삭제 가능·파기 완료 상태를 반환하지 않는다.** `REVIEW_REQUIRED`는 삭제 허가가 아니다.
- 범위: 신청에 특정된 문의는 해당 신청에만 적용한다. 신청을 특정하지 않은 경기 문의는 매칭 공용 계좌의 보류 사유로 잡으며, 본인의 경기 문의는 해당 신청에도 반영한다. 매칭 계좌는 원문이 없는 신청까지 포함해 모든 신청의 미해결 상태를 확인한다.
- 실행: 명시적인 점검용 DB 연결만 사용하고 `.env.local`·운영 연결을 자동 선택하지 않는다. 동일 시점의 읽기 전용 트랜잭션에서 페이지별로 점검한다. 상태 보정 함수·삭제·UPDATE를 호출하지 않는다. 실제 파기 때는 별도 잠금·재판정이 필요하다.
- 검증: 미입금 거절/만료, 종료 전 확정, 종료 후 미보정 신청, 늦은 입금, 부분·중복 환불, 송금 처리/재확인, 과거 추정 수령액, 문의 범위, 복사본, 빈 목록·페이지 경계·오류를 확인한다. 로컬 전용 DB에서 원문과 행이 점검 전후 동일한지 검증한다.

Q2의 채팅 기간과 나머지 미확정 정책, 크론 보류 결정은 유지한다. 실제 삭제 구현 전에는 최종 대조 기록·항목별 보존 예외·최소 거래 기록과 재수집 처리를 먼저 연결해야 한다.

### 11.1 실행·결과 읽기

구현: [판정](../src/server/domain/court-financial-retention.ts), [읽기 전용 조회·집계](../src/server/domain/court-financial-retention-audit.ts), [점검 명령](../prisma/audit-court-financial-retention.ts).

`RETENTION_AUDIT_DATABASE_URL`에 점검 대상 연결을 명시한 뒤 `npm run privacy:audit:financial`을 실행한다. 셸과 DB 조회 권한이 있는 내부 작업자가 사용하는 명령이며 공개 HTTP 경로는 없다. 원문을 조회하지 않아도 거래 건수는 내부 정보이므로 보고서를 공개 자료로 배포하지 않는다. 이번에는 임시 로컬 전용 DB만 사용하며 운영 DB 점검·파기는 실행하지 않는다.

- `scanned`: 조사한 코트 매칭·신청 수. 일반 매칭은 제외한다.
- `applicationsWithRaw`: 신청 행 또는 과거 송금 시도에 정리 대상 원문이 남아 있는 **신청 수**. 한 신청에 여러 복사본이 있어도 한 번 센다.
- `matchAccountsWithRaw`: 계좌 전체번호·예금주가 남아 있는 **매칭 수**.
- `rawLocations`: 신청 행·과거 송금 시도·매칭 행 각각의 원문 보유 **행 수**. 개인정보 항목 수나 중복 제거한 사람 수가 아니다.
- `retain`: 현재 미해결 업무 등 보존 필요가 확인된 건수.
- `reviewRequired`: 알려진 업무가 끝났더라도 최종 대조·보존 검토가 남은 건수. 삭제 승인 건수가 아니다.
- `reasons`: 고정된 한국어 설명과 사유별 건수. 여러 사유가 겹칠 수 있으므로 합계는 대상 수보다 클 수 있다.
- `assessedAt`: 점검한 DB 트랜잭션 시각. 모든 페이지는 이 트랜잭션의 일관된 스냅샷을 읽는다. 실행 후 바뀐 입금·환불은 다음 점검에 반영한다.

도구는 항상 `deletionEnabled: false`를 반환한다. 오류 시 보고서 일부를 출력하지 않고 실패 종료하며, DB 오류 원문·연결 문자열을 출력하지 않는다. 100개 경기씩 읽으며 개별 쿼리와 트랜잭션 유휴 시간에는 30초 제한을 둔다. 규모가 커져 제한에 걸리면 결과를 삭제 근거로 쓰지 않고 점검 방식을 다시 검토한다.

### 11.2 검증 결과 (2026-10-10)

- 단위 18개·실제 PostgreSQL 통합 7개를 추가했고, 기존 검증을 포함해 **59개 파일·458개 테스트 통과**. 타입 검사·린트·프로덕션 빌드 통과.
- 임시 PostgreSQL 17에 기존 33개 마이그레이션과 가상 데이터를 적용해 검증. 현재 환불 계좌가 비어 있어도 과거 송금 복사본은 집계되며, 점검 전후 원문·행이 동일함을 확인.
- 101개 경기의 페이지 경계, 점검 도중 다른 연결에서 발생한 갱신, DB 읽기 전용 모드, 오류 시 롤백·부분 결과 미반환 확인.
- 도움말, 전용 연결 누락, 잘못된 인자·연결, 가상 데이터 대상 명령 실행을 확인. 앱의 `DATABASE_URL`로 자동 연결하지 않으며 연결 값·원문을 오류에 출력하지 않음.
- 화면·공개 API·Prisma 스키마·크론 변경 없음. 운영 데이터 조회·파기·배포는 실행하지 않음. 새 화면이 없어 모바일 화면 검증 대신 실제 명령 실행을 확인.
- 전체 기존 DB 테스트에서 `pg`의 동일 연결 동시 쿼리 사용에 관한 차기 버전 경고가 출력됨. 테스트 실패는 없으며 이번 점검은 쿼리를 순차 실행함.

별도 후속 확인: 임시 DB의 `Asia/Seoul` 설정에서 기존 Prisma 어댑터로 날짜를 저장한 값과 PostgreSQL 절대 시각 사이에 9시간 차이가 재현됐다. 설치된 어댑터는 날짜 입력에서 시간대 표시를 생략하고 조회 시 오프셋을 `+00:00`으로 치환한다. 이번 점검은 PostgreSQL의 저장 시각과 DB 시계를 직접 비교하며, 동시 변경 테스트도 DB 시각으로 가상 일정을 변경한다. **운영 DB·연결의 시간대 설정과 실제 데이터 영향은 미확인**이며 기존 날짜 저장 로직은 이 작업에 섞어 수정하지 않았다.


## 12. 2026-10-10 후속: 대조·보존 기록

§11의 최초 도구 구현 이후 [03-20 금융 대조·보존 기록](03-20-financial-reconciliation-records.md)을 추가했다. 운영자/배정된 인계 담당자가 명시적으로 최종 은행 대조를 남기고 필요한 원문별 보존 사유를 등록·해제한다. 점검 도구는 유효한 대조, 이후 상태 변경, 보존 범위와 재검토 기한 경과를 구분한다. 보존 기록이 없어도 별도 보존 검토가 완료됐다는 의미는 아니며 `deletionEnabled: false`를 유지한다. 실행에는 `20261010010000_financial_review_records` 마이그레이션이 필요하다.

§11.2의 시간대 후속 확인도 진행했다. 운영 연결은 GMT였고 UTC 명시 연결을 지원했다. 앱·시드·테스트에 UTC 연결 옵션을 적용했으며 과거 운영 데이터의 일괄 정정은 하지 않았다. 이전 검증 결과는 당시 기록으로 유지한다. Q2와 실제 파기·재수집·복사본 및 메모 처리·법정 보존 근거의 미확정 항목, 크론 보류는 바뀌지 않는다.
