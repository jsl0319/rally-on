# 파일럿 전 점검 — 무엇이 남았나

작성일: 2026-09-12 · 확인 기준 커밋: `ef0a949`

## 0. 이 문서의 자리

[`03-9`](03-9-service-quality-review.md)가 "지금 잘못 동작하는 것"을 다뤘다면, 이 문서는
**서울·경기 파일럿으로 실제 사람을 받기 전에 끝내거나 정해야 하는 것**을 모은다. 기능
품질이 아니라 출시 가능 여부가 기준이다.

여기 적은 것은 대부분 다른 문서에 이미 흩어져 있다([`02-prd`](02-prd.md) §17,
[`06`](06-development-plan.md) §15.4·§23, [`07-m9`](07-m9-limited-user-test.md) §2,
[`08`](08-in-app-match-chat-design.md) §8.2, [`03-6`](03-6-court-match-operations-policy-review.md)
R05~R16, [`03-8`](03-8-court-match-service-continuity-review.md), [`09`](09-court-commerce-pg-preflight.md)).
이 문서의 값어치는 **모아 놓은 것과, 저장소 밖의 사실을 실제로 조회해 확인한 것**이다.

## 1. 오늘 확인한 사실 (저장소 밖)

운영 DB와 Vercel을 읽기 전용으로 조회한 결과다. 짐작이 아니다.

| 확인한 것 | 결과 | 뜻 |
| --- | --- | --- |
| 내부 심사자 계정 | **0명** | 운영자 승인·채팅 신고 처리·1:1 문의 답변·탈퇴 운영자 거래 인계가 **전부 막혀 있다** |
| `CRON_SECRET` (Production) | **있음** | 크론은 인증 때문에 실패하지는 않는다. 하루 한 번이라는 것은 별개 문제(`03-9` P1-5) |
| 운영 DB 마이그레이션 | 하나 빼고 모두 적용됨 | 미적용은 작업 중인 `20260912110000_court_application_notice` 하나뿐 |
| 개발·프로덕션 DB 분리 | **분리되어 있지 않다** | Vercel의 `DATABASE_URL`이 `Production, Preview, Development` 세 환경에 하나로 걸려 있다 |
| 운영 DB 안의 사람 | 실계정 **1명** (`auth_accounts=1`) | users 14명 중 13명은 시드(`[테스트] …`, `시드…`) |
| 운영 DB 안의 매칭 | 23건 전부 시드·테스트, 대부분 `EXPIRED` | 채팅 메시지 0건, 대화방 0개 |

두 가지가 여기서 곧바로 나온다.

**DB가 하나다.** 어제 마이그레이션이 의도치 않게 운영에 적용된 것이 이 때문이다.
시드 스크립트들은 이미 이 사실을 알고 upsert만 하며 아무것도 지우지 않는다
(`prisma/seed-court-match.ts` 주석에 이유가 적혀 있다). 사고는 나지 않았지만, 환경을
나누기 전까지는 로컬에서 도는 모든 것이 운영 데이터를 건드릴 수 있는 자리에 있다.

**지금이 정리하기 가장 쉬운 시점이다.** 실사용자가 한 명이고 대화 기록이 없다. 파일럿
사용자가 들어온 뒤에는 시드 데이터를 지우는 일이 훨씬 조심스러워진다.

## 2. 파일럿을 막는 것 — 사람이 답해야 하는 것

코드로 먼저 정할 수 없는 것들이다. [`07-m9`](07-m9-limited-user-test.md) §2가
"이 문서에 임의의 연락처나 보관 기간을 적지 않는다"고 못박은 이유다.

### D1. 운영 문의 채널 — 무엇이고 누가 받는가

앱 안 1:1 문의는 구현돼 있지만 **로그인하지 못하는 사람에게는 창구가 없다**
(`03-8` §2: "현재 확인된 외부 창구가 없으므로 '문의하세요' 문구만 추가해서 해결했다고
볼 수 없다"). 정할 것: 채널 종류, 응답 시간, 당번.

### D2. 채팅 메시지·신고의 보관 기간과 파기 방식 · 법무

[`08`](08-in-app-match-chat-design.md) §4.2가 **"이 결정 전에는 공개 채팅을 출시하지
않는다"**고 적은 유일한 항목이다. 권장안(종료 후 24시간 읽기 전용 → 30일 내 삭제 또는
비식별화)까지 이미 쓰여 있으므로 남은 것은 확정과 법무 확인이다.

### D3. 신고 검토 담당자·긴급 조치 권한·응답 시간

코드는 다 있다(`/internal/chat-reports`, 메시지 숨김·발신 중지·방 읽기 전용). 비어 있는
것은 운영이다 — 누가, 몇 시간 안에, 어떤 기준으로.

### D4. 운영 주체 — 사업자인가 개인인가

약관과 개인정보 처리방침의 "운영 주체", 개인정보 보호책임자, 계약상 지위가 모두 이 답에
달려 있다. `03-8` §4: "제공되지 않은 사업자 정보나 연락처를 임의로 만들지 않는다."

### D5. 크론을 재개할 것인가 · 사용자 결정

`AGENTS.md`가 명시적 재개 요청 전까지 보류로 못박았다. 재개하지 않는다면 **운영 절차가
이를 메워야 한다** — 시작 3시간 전 최소 인원 미달 취소를 사람이 눈으로 확인하는 당번이
생긴다(`03-6` R07: "정시 자동화 검증을 대체하지 못한다").

## 3. 파일럿을 막는 것 — 하면 되는 것

### B1. 내부 심사자 계정 지정 · 경로는 만들었다

운영 DB에 한 명도 없다. 지금까지는 손으로 UPDATE를 치는 수밖에 없었는데, 기록도 남지
않고 오타 한 번에 엉뚱한 계정이 권한을 갖는다. **웹에서 닿지 않는 전용 명령을 만들었다.**

```
npm run role:reviewer -- --list
npm run role:reviewer -- --grant "닉네임"
npm run role:reviewer -- --revoke "닉네임"
```

셸과 DB 접속 정보를 가진 사람만 실행할 수 있고, 어느 데이터베이스를 바꾸는지 먼저 보여
준 뒤 사람이 확인해야 적용된다. 대상이 여럿이면 거부하고, 활성 계정에만 부여하며, 바꾼
뒤 심사자 전원을 다시 센다. `04-erd.md`가 말한 "보호된 서비스 외 절차"를 손으로 치는
SQL 대신 되풀이 가능한 명령으로 만든 것이다.

**웹 화면이나 API로는 만들지 않았다.** 이 역할 하나로 사업자등록증 원문 열람, 채팅
메시지 숨김, 환불 실행이 모두 열리기 때문이다. 심사자가 다른 심사자를 임명하는 화면은
파일럿에서 두 명 이상을 운영하기로 정한 뒤에 따로 판단한다.

### B2. 개발·프로덕션 데이터베이스 분리

Vercel의 `DATABASE_URL`을 환경별로 나눠야 한다(Neon 브랜치). 이것이 없으면 로컬에서
도는 시드·마이그레이션·테스트가 전부 운영 데이터와 같은 자리에 있다. **대시보드 작업이라
코드로 끝낼 수 없다.**

### B3. 운영 DB의 시드 데이터 정리

사용자 13명과 매칭 23건이 시드다. 첫 파일럿 사용자가 `[테스트] 한강 블루 테니스장`을
보게 된다. 실계정이 하나뿐인 지금이 가장 싸게 정리할 수 있는 때다.

### B4. 최소 백업·복구 확인

`package.json`의 `vercel-build`가 `prisma migrate deploy`를 포함하므로 **배포 한 번이
운영 DB 스키마를 바꾼다.** 되돌리는 방법을 아직 한 번도 시험하지 않았다
(`06` §15.4의 미체크 항목). Neon의 복구를 한 번 해 보는 것이 최소치다.

### B5. 배포 후 확인 절차

`/api/health`는 `SELECT 1` 한 줄이라 **카카오 로그인이 깨진 것은 잡지 못한다.**
`06` §20.2의 smoke test를 실제로 돌리고, 프로덕션 카카오 앱의 Redirect URI가 실제
도메인으로 등록돼 있는지 확인해야 한다.

### B6. 오류를 사람에게 알리는 경로

`03-9` P0-2로 추적 번호(`X-Request-Id`)는 붙었지만 **알림은 없다.** 외부 오류 추적 도구
도입은 `06` §19가 비용·개인정보 검토를 요구하므로, 파일럿 최소치는 "하루 한 번 로그를
보는 당번" 같은 절차일 수 있다.

## 4. 돈이 오가기 전에 — 코트 매칭 유료 운영

`03-6` R05~R16 중 미해결분이다. 별도 작업으로 진행 중인 것이 있어 여기서는 목록만 든다.

- R05 경기 구성(혼복 남4·여0이 통과한다) · R06 계약 역할·면책·환불율 적법성(법무)
- R07 거래 알림이 "매칭 알림" 토글에 막힌다 · R08 자정 경계에서 취소 금액이 바뀐다
- R09 승인·입금·대조 시간표의 숫자가 비어 있다 · R10 취소 사유 우선순위와 부분 이용
- R11 운영자 중지 후 기존 거래 · R12 무료 코트 매칭 허용 여부 · R13 재신청 허용 여부
- R14 환불 계좌 보관 기간과 담당자 접근 범위 · R15 누락 없는 운영 목록

PG 연동([`09`](09-court-commerce-pg-preflight.md))은 이 뒤다. 다만 **문의를 보내기 전에
결제 주체를 다시 정해야 한다** — `09`의 RFI 초안은 모집자 한 명이 코트 총액을 결제하던
옛 모델을 전제하는데, 코트 매칭의 주최자는 이미 운영자로 바뀌었다(`02-prd` L107이 같은
경고를 남겼다).

## 5. 파일럿 체감에 가장 큰 것

막는 것은 아니지만, 파일럿이 성공하느냐에 직접 걸린다.

1. **새 메시지 알림**(`03-9` P0-3) — 수락 뒤 "몇 시에 만날까요?"가 전달되지 않으면 약속
   조율이 끊긴다. 방마다 하나로 묶고 읽으면 지우는 방식이 맞다고 본다.
2. **시작 전 리마인더**(`03-9` P2-13) — 노쇼를 줄이는 가장 싼 장치. 알림 종류 추가가
   1번과 겹치므로 함께 하는 편이 낫다.
3. **매칭 개설 폼**(`03-9` T-10) — 3,700픽셀 한 장. 온보딩은 단계로 나눴는데 정작 가장
   어려운 화면이 안 나뉘어 있다.
