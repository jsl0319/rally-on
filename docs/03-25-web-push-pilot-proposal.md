# 소규모 운영용 외부 푸시 검토

2026-10-10 최초 제안. **2026-10-14 사용자 승인으로 웹 푸시 구현을 진행한다.** 과거 제안·보류 기록보다 아래 최신 구현 범위를 우선한다.

> **이전 결정 기록(아래 2026-10-14 웹 푸시 승인 전):** Android와 iOS 스토어에서 다운로드하는 설치형 앱 출시를 우선 검토했다. 당시 스토어 출시 목표에 대한 답변만으로 Web Push 구현을 승인한 것으로 해석하지 않았다. 현재는 문서 마지막의 웹 푸시 구현 승인과 범위를 따른다.

> **후속 승인:** 사용자가 1번 앱 전환 구조 검증을 요청했다. 독립 개발 시제품과 기기별 검증 상태는 [03-26](03-26-native-app-prototype.md)을 따른다. 푸시 구현·스토어 출시 완료를 뜻하지 않는다.

> **2026-10-14 현재:** 설치형 앱 코드·문서의 인수인계 검토를 마쳤다. 사용자는 무료 Personal Team만 사용 중이다. 기존 앱 검증을 유지하며 실제 외부 푸시는 아직 연결하지 않았다. 다음 작업과 계정 준비 조건은 마지막 절을 따른다.

## 사용자 문제와 최소 범위

입금·확정·경기 취소를 앱 밖에서도 알아야 참가자와 운영자가 이동/대관을 결정할 수 있다.
최초 검토 당시 앱은 DB의 인앱 알림만 제공했고 manifest·service worker·push subscription은 없었다.
크론은 기한에 상태를 처리하는 장치이고 푸시는 생성된 결과를 기기로 보내는 장치다.
푸시를 추가해도 미실행 크론의 판정 결과가 저절로 생성되지는 않는다.

## 무료 선택지

1. **표준 Web Push + 홈 화면 웹앱 권장.** 기존 Next 서버와 DB를 유지하고 브라우저 푸시 서비스에 전달한다. Apple Developer 유료 가입 없이 iOS Web Push를 사용할 수 있다. 별도 상용 푸시 대시보드가 필요하지 않다. 전송 서버·구독 저장·재시도는 기존 호스팅 사용량에 포함되므로 전체 운영 무료를 보장하지 않는다.
2. **Firebase Cloud Messaging 대안.** FCM 자체는 무료이고 웹/Android/iOS를 지원한다. 다만 Firebase 프로젝트/키 관리와 SDK 통합이 추가되며 웹의 설치·권한 제약을 없애주지는 않는다. 인증·DB를 Firebase로 옮길 필요는 없다.

iOS/iPadOS 16.4 이상은 홈 화면에 추가한 웹앱에서 사용자가 버튼을 누른 뒤 권한을 요청해야 한다. 일반 Safari 탭에서 앱 실행 직후 권한을 강제로 띄우는 흐름으로 구현하지 않는다. Android/데스크톱도 실제 Push API·Service Worker 지원 여부를 검사한다. 앱 안의 카카오 브라우저 등 미지원 환경에는 외부 브라우저/홈 화면 안내를 제공한다.

## 알림 동의 강제에 대한 권장 의견

앱 전체를 알림 동의로 잠그는 방식은 권장하지 않는다. 미지원 환경·기기 변경·권한 차단 사용자가 기존 신청/환불/운영 연락을 확인할 길까지 막힐 수 있다. 앱 실행 때 이유를 설명하고 사용자가 누른 ‘알림 켜기’에서 OS 권한을 요청하는 안을 제안한다. 거부해도 기존 거래·문의에는 계속 접근할 수 있어야 한다.

- 신청 전과 운영자의 첫 공개 전: 알림을 켜면 받을 중요한 정보를 설명하고 설치/권한 설정 유도.
- 꺼진 상태: ‘앱 밖에서 입금·취소 안내를 받을 수 없어요. 진행 여부를 앱에서 직접 확인해 주세요.’
- 앱 안의 알림 끄기: 진행 중인 신청이 있으면 위 영향을 한 번 안내하고 최종 선택은 존중.
- OS 설정에서 끄기: 앱이 그 순간 경고하거나 해제를 막을 수 없다. 앱 복귀 시 권한·구독 상태를 다시 확인해 알린다. OS 집중 모드 등 모든 전달 차단 상태를 앱이 검출할 수 있는 것은 아니다.
- 미지원/거부 상태를 반복 권한 팝업으로 압박하지 않는다. 거부 뒤에는 브라우저 설정 안내를 제공한다.
- 허용 여부나 전송 서버 접수 성공은 기기의 수신/읽음 증거가 아니다. 푸시만으로 합의·진행 확정·환불 동의를 간주하지 않는다.

## 승인 후 최소 구현안

- manifest, 설치 안내, 푸시 수신 전용 service worker. 인증 API/거래 화면 오프라인 캐시는 만들지 않는다.
- 사용자·기기별 구독 저장/삭제, 본인 권한 검사, 로그아웃/계정 전환/탈퇴 때 이전 계정 연결 해제.
- 검증된 Web Push 라이브러리와 VAPID 비밀키. 프로덕션 의존성 추가는 별도 합의 후 진행.
- 상태 DB 커밋 후 전송. 송신 장애 때문에 입금·취소 자체를 롤백하지 않는다. 작은 재시도 기록/중복 방지, 만료 구독 정리, 실패 건수 확인.
- 잠금 화면에 계좌번호·실명·자기소개를 보내지 않고 ‘참가 상태가 변경됐어요’와 로그인 후 상세 링크 제공.
- 먼저 확정·취소·입금 확인 필요 등 거래 알림만. 마케팅·범용 채팅 푸시는 별도 범위다.
- iPhone 홈 화면 앱과 Android에서 앱을 닫은 수신, 거부/해제, 계정 전환, 만료 구독, 중복 전송, 실패 복구를 실제 기기로 검증.

새 푸시 플랫폼이나 앱스토어 앱보다 위 범위가 단순하다. 다만 현재 기한 안전장치와는 별도 검토 단위이며, 즉시 무조건 도착하는 알림을 보장하는 기능으로 표현하지 않는다.

## 설치형 앱 출시 방향으로 변경 (2026-10-10)

사용자는 홈 화면 웹앱에 한정하지 않고 Android·iOS에서 다운로드해 사용하는 앱 출시를 원한다. 앱을 닫은 상태의 거래 알림을 제공하고 스토어에서 설치할 수 있게 하는 것이 목적이다. 기존 매칭·입금·환불 백엔드는 유지하며, 앱 패키징과 기기 연동은 별도 작업 단위로 검증한다. 이번 변경은 조사·계획 기록이며 새 SDK·앱 프로젝트·유료 개발자 가입은 실행하지 않았다.

### 권장하는 작은 첫 작업

1. 기존 React 화면 재사용을 위해 Capacitor를 첫 후보로 비교한다. React Native/Flutter 전체 재작성은 현 단계의 기본안으로 삼지 않는다. 더 단순한 대안은 기존 웹 운영과 홈 화면 설치지만, 스토어 다운로드라는 사용자 목표를 완전히 충족하지 않는다.
2. 로그인 → 목록/상세 → 앱 복귀와 외부 링크 → 알림 클릭으로 상세 열기만 우선 검증하는 작은 시제품을 만든다. 통과 후 신청·취소·환불·사진 업로드 등 핵심 흐름을 확장 검증한다. 새 의존성·인증 변경·앱 배포 구조는 검증 범위와 함께 합의하고 적용한다.
3. 현재 `src/app/page.tsx`는 서버 인증·DB 조회를 사용하고 `src/auth.ts`의 공급자는 Kakao 하나다. Next 서버 전체를 정적 파일로 포장할 수 있다고 가정하지 않는다. 서버는 유지하고 패키징할 클라이언트 경계, API 인증, 쿠키/로그인 콜백과 외부 브라우저 복귀를 먼저 정한다. 공식 Capacitor `server.url`은 개발용 live reload 설정이므로 운영 URL 하나를 넣고 출시 완료로 처리하지 않는다.
4. Android는 FCM, iOS는 APNs 기반 네이티브 푸시를 우선 비교한다. FCM은 자체 전송료가 없으며 iOS도 연동할 수 있지만 Apple 설정과 별도 SDK 연동이 필요하다. Capacitor 기본 push 플러그인의 iOS 토큰은 APNs 토큰, Android는 FCM 토큰이므로 서로 같은 전송 API에 그대로 넣지 않는다. Firebase로 인증·DB를 이전할 필요는 없다.

### 동의와 출시 전 확인

- **푸시 강제 동의는 적용하지 않는다.** Apple 심사 지침 4.5.4는 푸시를 앱 동작의 필수 조건으로 두지 못하게 한다. 중요 단계의 선택 동의 안내와 해제 시 영향 설명을 제안한다. 실제 OS 권한 해제는 앱 복귀 때 확인하며, 기존 거래·환불·문의 접근을 유지한다. 사용자에게 이 제약과 제안을 설명한 상태로, 동의 UX 구현은 아직 하지 않았다.
- 기존 Kakao 단독 로그인은 Apple 4.8의 동등한 개인정보 보호 로그인 선택지 요구에 해당하는지 확인한다. 현 서비스에는 뚜렷한 예외를 확인하지 못했으므로 Apple 로그인 추가를 예상 작업으로 잡되, 계정 중복/연결 정책을 정하기 전 임의로 인증을 교체하지 않는다.
- Apple 4.2의 앱 완성도 요구를 고려한다. 웹사이트를 단순히 감싼 형태로 심사 통과를 보장하지 않는다. 네이티브 푸시·앱 내 이동·복귀·키보드·뒤로가기·네트워크 오류를 실제 기기로 검증한다.
- 채팅/사진의 사용자 생성 콘텐츠 신고·차단 대응, 앱 내 계정 삭제, 개인정보 공개와 심사용 접근을 현재 구현과 대조해야 한다. 대규모 기능을 임의 추가하기보다 스토어 필수 조건의 실제 공백부터 확인한다.
- 무료 푸시와 무료 스토어 출시는 다르다. Apple Developer는 연 USD 99(지역별 결제액 차이), Google Play는 등록 시 USD 25 일회 비용이다. 개인 Apple 계정은 법적 실명이 판매자명으로 표시된다. 결제·가입은 별도 승인 없이 진행하지 않는다.
- Google Play의 2023-11-13 이후 생성 개인 계정은 최소 12명의 테스터가 14일 연속 참여한 비공개 테스트 후 프로덕션 접근을 신청해야 한다. 계정 보유/생성 시점과 테스트 인원은 아직 확인하지 않았다. 출시일을 확정하기 전에 준비한다.

## 2026-10-14 인수인계 검토와 다음 작업

### 확인 결과

사용자가 기존 Claude 작업을 설치형 앱·푸시로 확인했다. 시제품 소스는 저장소에 반영됐고 17개 검사가 통과했다. 푸시 문서는 제안 단계이며 네이티브 플러그인·기기 등록·서버 발송은 구현되어 있지 않다. 기존 알림 DB와 관리자 문의 처리 알림을 유지한다.

사용자는 유료 Apple Developer Program에 가입하지 않았다고 답했다. Apple의 [iOS 지원 기능 표](https://developer.apple.com/help/account/reference/supported-capabilities-ios)에서 `Push notifications`는 유료 프로그램에만 표시되며 무료 계정에는 없다. 따라서 현재 무료 서명 앱으로 APNs 실기기 수신을 완료할 수 없다. 시뮬레이터의 알림 주입이나 로컬 예약 알림은 대체 검증이 아니다. FCM을 사용하더라도 iOS에서는 APNs 설정이 필요하다([Firebase iOS 설정](https://firebase.google.com/docs/cloud-messaging/ios/get-started)). 가입·결제·인증서·푸시 키 생성은 실행하지 않았다.

무료 Personal Team의 설치 프로파일은 발급 후 7일이 지나면 재빌드·재설치가 필요하다. 검증 앱이 나중에 열리지 않을 때에는 앱 코드 오류와 서명 만료를 구분한다([Apple 계정 안내](https://developer.apple.com/help/account/basics/about-your-developer-account)).

### 다음 구현 단위 제안

해결할 문제는 신청·확정·취소 결과를 앱 밖에서도 알아야 한다는 것이다. 기존 매칭 흐름에 작은 알림 전달 경로를 추가하며 인증·DB를 다른 서비스로 옮기지 않는다. 새 의존성·기기 등록 데이터·발송 경로와 실제 수신 검증이 추가되므로 단순 UI 수정과 분리한다. 더 단순한 대안은 당분간 인앱 알림을 유지하거나 홈 화면 Web Push를 별도 구현하는 것이지만, 후자는 현재 설치형 앱의 네이티브 푸시를 완성하는 작업은 아니다. 사용자 요청 없이 웹 푸시로 방향을 바꾸지 않는다.

1. **현재 iPhone 시제품의 남은 흐름 검증:** 인증 취소 후 앱 복귀, 키보드가 입력·버튼을 가리지 않는지, 로그아웃 뒤 뒤로가기 캐시에서 보호된 데이터가 보이지 않는지 확인한다. 지도 앱 미설치와 최신 브랜드 콜드 스타트 전환은 미검증 상태를 유지한다. Android 실기기는 사용자 재개 요청 후 진행한다.
2. **계정 준비 후 본인 기기 1대에 거래 알림 연결:** 우선 iOS APNs, 이후 Android FCM을 연결하는 안이다. Capacitor 기본 플러그인은 두 플랫폼에서 서로 다른 종류의 토큰을 반환하므로 플랫폼·개발/운영 환경·앱 식별자를 구분해 발송한다. 관련 SDK 추가와 실제 외부 연결 범위를 합의한 뒤 구현한다. APNs 키는 서버에만 보관한다.
3. **기기와 계정 연결 보호:** 로그인한 본인만 기기를 등록한다. 로그아웃·탈퇴·계정 전환 시 이전 수신자 연결을 해제하고 전송 직전에도 활성 계정·현재 연결을 재확인한다. 토큰 갱신과 만료를 처리한다. 권한 거부 상태에서도 기존 거래·환불·문의에 접근할 수 있어야 한다.
4. **기존 인앱 알림에서 발송:** 거래 결과와 발송 대상을 같은 DB 트랜잭션으로 기록하고 커밋 후 전송한다. 발송 실패가 거래를 취소하지 않게 하며, 알림·기기별 중복 작업 방지와 횟수 제한 재시도만 둔다. 전송 접수·실제 기기 표시·사용자 열람은 다른 상태로 취급한다. 확정·취소·입금 확인 등 거래 알림부터 시작하며 마케팅과 채팅 푸시는 별도 범위다.
5. **안전한 알림 이동과 완료 기준:** 잠금 화면에는 계좌·실명·메시지 본문을 노출하지 않는다. 알림 클릭으로 허용된 앱 내 경로만 열고 로그인 및 해당 거래 접근 권한을 다시 검사한다. 앱 종료/복귀·거부/해제·계정 전환·중복·만료 토큰·발송 장애를 확인한 뒤 실기기 성공으로 기록한다.

위 항목은 다음 작업 제안이며 구현 완료나 새 SDK·유료 가입 승인으로 해석하지 않는다. 현 검토에서 네이티브 소스·웹 인증·운영 DB·크론은 변경하지 않았다.


## 2026-10-14 웹 푸시 구현 승인과 범위

사용자가 모바일 웹·iOS·Android 모두 운영하기 위해 무료 웹 푸시부터 구현하도록 승인했다. 기존 인앱 알림의 사건·이동 경로를 재사용하고 전송 어댑터만 Web Push로 구현한다. 검증된 `web-push` 라이브러리 1개를 추가하며 상용 서비스 가입·Apple 멤버십 결제·네이티브 SDK는 포함하지 않는다. 인앱 알림만 유지하는 대안은 앱 밖의 중요 변경 인지 문제를 해결하지 못한다.

- 마이의 알림 화면에서 사용자가 직접 켜고 끈다. iOS 일반 탭은 홈 화면 추가를 안내하고 네이티브 검증 앱은 별도 준비 중으로 안내한다. 권한을 거부해도 앱을 계속 이용한다.
- 알림 원본은 기존 DB 트랜잭션으로 생성한다. 커밋된 원본만 발송 작업으로 전개하고, 응답 후 즉시 전송을 시도한다. 기존 15분 크론은 누락·실패를 재시도한다. 푸시 실패는 거래 결과를 바꾸지 않는다.
- 구독은 사용자·브라우저별로 관리한다. 등록·해제는 동일 출처 인증 요청만 허용한다. 로그아웃/탈퇴/계정 변경 때 연결을 삭제하며 알림 표시 시에도 브라우저의 현재 연결을 대조한다.
- 잠금 화면은 서비스의 새 알림 안내만 보여준다. 실명·금액·코트명·본문은 전송하지 않는다. 클릭하면 알림 소유권과 로그인 확인 뒤 기존 상세로 이동한다.
- 새 구독 전의 알림은 소급 전송하지 않는다. 원본·구독별 유일 작업, 작업 임대, 최대 4회 시도, 24시간 유효기간을 둔다. 공급자 접수 직후 서버가 중단된 경우 재발송 가능성은 남고 같은 알림 태그로 중복 표시를 줄인다. 접수 성공을 실수신으로 표시하지 않는다.
- 만료 구독(404/410)은 삭제한다. 비활성 계정은 전송하지 않는다. 30일간 갱신되지 않은 연결·7일 지난 발송 이력은 기존 크론에서 정리한다. endpoint와 구독 키는 로그·응답·문서에 노출하지 않는다.
- 기능은 기본 꺼짐이다. 서버 환경의 활성화 플래그와 VAPID 공개/비밀키가 모두 있어야 켤 수 있다. 운영 적용·실제 iPhone 홈 화면 수신은 구현 검증과 별도로 기록한다. 서버/DB 무료 사용량 안에서 운영하며 전체 무료나 정시 도착을 보장하지 않는다.


### 활성화·점검·중지 절차

1. `node ops/push/generate-vapid.mjs`로 Git 제외 폴더에 0600 권한의 키 파일을 만든다. 같은 파일을 덮어쓰지 않는다. 값을 로그·메시지·커밋에 붙이지 않는다. 개발/운영 키는 분리한다.
2. 운영 반영 승인 후 백업 지점·추가형 migration 호환성을 확인하고 `20261014010000_web_push`를 적용한다. 기존 운영 코드와 데이터는 유지된다.
3. Vercel 서버 환경에 `WEB_PUSH_ENABLED`, `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_PRIVATE_KEY`, `WEB_PUSH_SUBJECT`를 등록한다. 공개키만 인증된 설정 API를 통해 브라우저에 전달한다. 비밀키는 서버에만 둔다. 환경 변경은 새 후보 배포에서 확인 후 `docs/11-production-release.md` 절차로 승격한다.
4. Safari → 홈 화면 추가 → 새 랠리온 아이콘으로 로그인 → 마이 → 알림에서 켜기 → 테스트 알림. 앱을 나간 상태의 표시·클릭 이동·로그아웃 뒤 차단을 실제 iPhone에서 확인한다. 설치형 `랠리온 검증` 앱의 네이티브 푸시 성공으로 기록하지 않는다.
5. 무료 크론의 `push.dispatch.completed/failed` 로그와 `npx tsx ops/push/check-status.ts`의 대기·실패·제공사 접수 건수를 확인한다. 점검은 선택된 DB를 읽기만 한다. 원문 endpoint·키·본문은 출력하지 않는다. 초기에는 매일 확인하고 20분 이상 미처리·실패 증가 시 설정/제공사 상태를 확인한다.
6. 중지하려면 `WEB_PUSH_ENABLED=false`를 새 배포에 반영한다. 인앱 알림과 거래·크론 판정은 계속 동작한다. 키 교체 시 기존 브라우저에서 알림을 끄고 다시 켜야 하며 구독을 자동으로 이전했다고 간주하지 않는다.

브라우저 푸시 서비스의 접수 성공과 실기기 도착은 다르다. 크론 HTTP 성공 또한 푸시 성공을 보장하지 않는다. 초기에는 위 발송 이력 점검을 병행하며 별도 유료 감시 서비스는 도입하지 않는다.
