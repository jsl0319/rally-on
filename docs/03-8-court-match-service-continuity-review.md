# 코트 매칭 운영 연속성·경기 제공·취소 고지 검토

검토일: 2026-09-11 · 구현 기준: `c012502` · 대상: `03-6` R04~R06

이 문서는 최초 검토와 권장안을 보존한다. **2026-09-11 사용자 승인 이후 R04 거래 연속성 구현은 [03-10](03-10-account-transaction-continuity.md)을 따른다.** 아래의 기존 동작/결정 필요 표시는 검토 당시 기준이다. R05/R06의 구현 완료를 뜻하지 않는다. 정본 `03-2`의 기존 정책과 충돌하는 부분을 명시한다. 첫 작업의 입금 예외·환불 실행·문의 처리는 `03-7`을 따른다. 이번 후속 검토에서는 운영 DB에 테스트 데이터를 넣지 않았고, 크론 보류를 유지했다.

## 1. 우선 결론

돈의 기록을 정정할 수 있게 됐지만, **돈을 돌려줘야 할 사람이 탈퇴하거나 운영을 중지하면 누가 처리를 이어가는지**는 아직 정해지지 않았다. 또한 입금 확정 인원만으로는 판매한 복식 경기를 실제로 제공할 수 있는지 판단할 수 없다. 참가자가 신청한 조건과 운영자가 바꾼 조건을 구분하는 기록도 필요하다.

| 우선순위 | 실제 운영에서 생기는 일 | 현재 공백 | 권장 다음 조치 |
| --- | --- | --- | --- |
| P1 | 참가자가 환불 계좌 입력 전에 탈퇴 | 인증 차단으로 계좌·문의 접근 불가 | 탈퇴와 거래 정리를 분리하고 제한된 접근 경로 제공 |
| P1 | 운영자 또는 담당자가 탈퇴·중지 | 입금·환불 대조 또는 문의 담당이 고립됨 | 업무 인계와 사유별 잔여 처리 권한 |
| P1 | 혼복인데 남자만 확정되거나 복식에 1~3명만 남음 | 최소 인원 숫자와 실제 경기 구성이 다름 | 유형별 최소 구성 및 진행 불가 처리 |
| P1 | 판정 후 취소로 경기 제공 불가 | 경기 유지 정책과 남은 참가자 보호가 충돌 | 개인 취소와 운영 사유 취소를 구분 |
| P1 | 당일 미확정 입금 후 철회 | 실제 전액 반환 로직과 약관의 포괄적 당일 환불 없음 문구 불일치 | 확정 여부·초과분을 구분한 고지 |
| P1 | 고객이 사고·공급 불가에 이의 제기 | 책임 면제처럼 읽히는 문구, 계약 역할·고지 이력 부족 | 사실·계약 역할 확인 후 핵심 조건과 약관 정비 |

배포 성공은 유료 운영 준비 완료 판정과 다르다. 아래 미확정 사항을 현재의 화면이나 자동 환불율로 임의 확정하지 않는다.

## 2. R04 — 탈퇴·중지 후에도 끝내야 하는 거래

### 확인한 동작

- [계정 탈퇴](../src/server/domain/account-service.ts#L12)는 User를 `WITHDRAWN`으로 바꾸고 직접 업로드한 사진을 지운다. 미래 경기·환불·담당 문의 조회나 인계는 없다. 거래 처리와 공유하는 잠금도 없다.
- [인증](../src/server/auth/current-user.ts#L22)은 비활성 회원의 모든 일반 API 접근을 막는다. 참가자는 반환 잔액이 있어도 계좌를 입력하거나 문의 답변을 확인할 수 없다.
- 운영자가 탈퇴해도 운영자 신청의 공개 승인과 시설 ACTIVE 상태는 그대로다. [공개 목록](../src/server/domain/court-slot-service.ts#L781)과 [신규 참가 검사](../src/server/domain/court-match-service.ts#L129)는 주최자 User의 ACTIVE 여부를 조회하지 않는다. 따라서 일정·정원 조건이 맞으면 **탈퇴한 운영자의 경기에 새 신청과 자동 승인이 계속 가능한 코드 경로**가 있다. 탈퇴한 참가자의 기존 자리도 자동 반환되지 않는다. 거래 접근 문제와 함께 신규 피해 유입을 먼저 막아야 한다.
- [금전 처리 권한](../src/server/domain/court-match-money-service.ts#L22)은 원래 주최자와 코트 운영자 일치를 요구한다. 내부 담당자는 문의를 처리할 수 있지만 탈퇴한 운영자의 입금·송금 결과를 대신 기록할 수 없다.
- [공개 중지·시설 비활성화](../src/server/domain/operator-publish-control-service.ts#L20)는 운영자/시설 상태와 사진 만료를 바꾸며, 기존 경기 취소·금전 인계는 하지 않는다. 반면 [참가 진행 검사](../src/server/domain/court-match-service.ts#L129)는 승인 중지/시설 비활성 상태의 기존 승인 건 입금 알림·참가 확정도 막는다.
- 첫 작업에서 금전 대조·환불 API는 공개 승인 상태를 요구하지 않도록 분리했다. 따라서 **계정이 ACTIVE인 공개 중지 운영자는 기존 반환 업무를 수행할 수 있다.** 계정 자체가 탈퇴·정지되면 여전히 접근할 수 없다. 두 종류의 중지를 혼동하면 안 된다.
- [문의 처리](../src/server/domain/support-service.ts)는 이미 다른 담당자가 배정됐으면 재배정을 허용하지 않는다. 담당자 계정이 비활성화되면 새 담당자가 맡을 수 없는 경우도 생긴다.
- [카카오 재로그인](../src/auth.ts#L81)은 기존 계정의 사진 URL을 갱신하고 로그인을 허용한 다음 일반 API에서 비활성 상태를 차단한다. 제한된 거래 접근을 만들 때 이 경로가 계정 복구나 불필요한 프로필 재수집으로 이어지지 않도록 정리해야 한다.

### 권장 정책 — 결정 필요

**탈퇴는 허용하되 남은 거래를 인계한다.** 환불을 끝내야만 탈퇴할 수 있도록 일괄 차단하는 안은 권장하지 않는다.

| 대상 상태 | 새 신청·모집 | 기존 일정 | 입금·반환 | 문의·기록 |
| --- | --- | --- | --- | --- |
| 참가자 탈퇴 | 차단 | 시작 전 신청 처리 결과를 별도 확인 | 본인 인증 후 본인 거래의 계좌·반환 상태만 접근 | 해당 거래의 문의·답변만 접근 |
| 운영자 행정상 공개 중지 | 차단 | 담당자가 시설 제공 가능 여부 확인 | 기존 대조·반환은 허용 | 원래 거래와 대조 요청만 |
| 시설 폐쇄·안전 중지 | 차단 | 영향 경기별 취소·후속 조치 | 참가 확정은 막고 실제 입금 대조·반환 유지 | 취소 이유·담당자·처리 결과 기록 |
| 운영자 계정 탈퇴/정지 | 차단 | 담당자에게 대상 경기 인계 | 제한된 담당자 대리 기록 경로 | 원래 운영자의 거래 책임은 계정 상태와 분리 |
| 내부 담당자 탈퇴/업무 중지 | 해당 없음 | 해당 없음 | 맡은 사건을 재배정 | 이전·이후 담당자, 사유, 시각 기록 |

참가자 탈퇴가 곧바로 확정 참가의 자발적 취소가 되는지는 별도 결정해야 한다. 권장안은 탈퇴 확인 단계에서 미래 신청별 자리 반환과 예상 금액을 안내하고, 확인한 취소와 탈퇴를 같은 작업으로 처리하는 것이다. 기존 날짜별 환불 규칙의 법적 적용은 §4 검토가 선행돼야 한다. 경기 시작 이후에는 무조건 자발적 취소/노쇼로 바꾸지 않고 거래 이력을 유지한다.

제한된 접근은 기존 카카오 본인 인증을 재사용할 수 있다. 일반 `getCurrentUser()`의 차단을 풀지 말고 본인 거래 조회·계좌·문의에만 사용할 별도 권한 검사를 둔다. 프로필 편집·매칭 신청·일반 채팅 접근이 함께 되살아나면 안 된다. 제한 접근의 종료 조건과 재가입 정책도 명시해야 한다.

더 단순한 파일럿 대안은 탈퇴 시 사건 번호와 **실제로 운영하는 비로그인 문의 창구**를 제공하고 담당자가 본인을 확인해 거래를 정리하는 방식이다. 현재 확인된 외부 창구가 없으므로 “문의하세요” 문구만 추가해서 해결했다고 볼 수 없다. 새 외부 서비스가 필요하면 별도 선택이 필요하다.

### 최소 구현 범위와 경계

1. 탈퇴 미리보기에서 미래 신청·운영 경기·미확인 입금 가능 건·미지급/처리 중/확인 필요 환불·미해결 담당 문의를 조회한다. 반환액 0원만으로 업무 종료를 판단하지 않는다.
2. 탈퇴 처리와 새 신청/승인의 경쟁을 막는 일관된 사용자·매칭 잠금 순서를 정한다. 인증 시점 이후 탈퇴한 사용자가 새 거래를 만드는 경우를 차단한다.
3. 거래 접근 범위와 `SupportInquiry` 재배정 이력을 추가한다. 운영자 자리를 다른 사용자 ID로 단순 교체해 과거 행위자를 덮어쓰지 않는다.
4. 담당자가 타인의 계좌나 송금 결과를 기록할 때 본인 확인 근거·실제 처리자·원래 책임자·사유를 남긴다. 이전의 처리 중 송금을 실패로 임의 전환하거나 두 번 송금하지 않는다.
5. 불필요한 프로필과 보존 의무가 있는 거래 정보의 저장 목적·항목·접근자·종료 조건을 구분한다. “탈퇴했으니 전부 즉시 삭제”와 “돈 문제니까 전부 영구 보관” 모두 피한다.

개인정보 보호법 제21조는 불필요해진 정보의 파기와 다른 법령에 따른 보존 시 분리 관리를 구분한다. 모든 프로필·채팅·환불 계좌에 동일한 기간을 적용할 근거는 아니다. 실제 보존 근거와 기간을 정보별로 확인해야 한다. [국가법령정보센터 제21조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0021&lsiSeq=270351&urlMode=lsScJoRltInfoR)

## 3. R05 — 판매한 경기와 실제 가능한 경기

### 재현 결과와 정책 충돌

`courtSlotCreateInputSchema.safeParse()`를 메모리에서 직접 실행했다. 미래 일정·정원 4·최소 1·혼복 남 4/여 0 입력과, 남복 정원 4·최소 1 입력이 모두 통과했다. DB를 수정하지 않고 확인했다. 현재 스키마는 정원 합계를 검사하지만 실제 진행 가능한 복식 구성은 검사하지 않는다.

[판정 함수](../src/server/domain/court-match-service.ts#L166)는 판정 이후 자발적으로 취소한 사람도 당시 확정 인원으로 센다. [정본 `03-2` §3.2·§3.7](03-2-court-match-operator-hosted-redesign.md)대로 구현돼 있으며, 이를 단순히 현재 인원 집계로 바꾸면 이전에 막은 전체 자동 취소 문제가 재발한다.

**충돌:** 기존 정책은 판정 이후 경기 유지를 보장하지만, 복식 4명 중 2명이 취소하면 남은 2명에게 같은 경기를 제공할 수 없다. 남은 사람에게 “본인이 취소하면 당일 환불 0원”만 제시해서는 제공 불가 상황을 해결할 수 없다.

### 권장안: 파일럿에서는 실제 가능한 구성만 판매

| 유형 | 공개 시 최소 구성 제안 | 진행 판정 제안 |
| --- | --- | --- |
| 혼복 | 최소 인원 4 이상, 남녀 정원 각각 2 이상 | 전체 최소 인원 충족 + 확정 남 2/여 2 이상 |
| 남복 | 최소 인원 4 이상, 여자 정원 0 | 최소 인원 이상의 남자 확정 |
| 여복 | 최소 인원 4 이상, 남자 정원 0 | 최소 인원 이상의 여자 확정 |
| 기타 | 최소 2 이상과 실제 제공할 플레이 안내 | 안내한 최소 인원 충족. 혼복/복식 제공으로 오인시키지 않음 |

운영자는 현 모델에서 플레이어가 아니므로 자동으로 네 번째 선수로 계산하지 않는다. 운영자가 별도 선수를 공급하는 상품은 실제 인원·역할·보장 조건을 모델링한 뒤 지원하는 대안이다. 한 코트의 최대 모집 인원이 커질수록 교대·대기 시간이 늘므로 이용 안내에서 경기 시간 전체가 개인의 실제 플레이 시간을 뜻하지 않도록 한다.

판정은 한 번 통과하는 관문으로 유지하되, 그 뒤의 **현재 제공 가능 여부**를 별도로 계산한다. 취소·운영 중지·현장 이슈로 구성이 깨지면 조치 필요 상태를 만들고 사유를 남긴다. MVP 권장안은 약속한 구성을 제공하지 못하면 운영 사유로 취소하고 영향을 받은 참가자의 실제 수령액을 전액 반환하는 방식이다. 기존 자발적 취소자에게 추가 반환이 발생하는지, 공급 불가 원인의 우선순위는 별도 결정한다.

대안은 참가자가 명시적으로 동의한 랠리/시간 변경 등 대체 진행이다. 이 경우 동의하지 않은 사람의 취소를 자발적 취소로 보지 않아야 하며, 누가 언제 무엇에 동의했는지와 금액 조정을 저장해야 한다. 초기 파일럿에는 변경 제안·개별 동의·시간 제한·인원 재계산까지 늘어나므로 단순 취소·반환안보다 범위가 크다.

추가 모집으로 복구할 수 있는 기간은 이미 확정된 신청/입금 기한 안으로 제한한다. 시작 90분 전이 지났는데 운영자가 임의로 자리를 더 받거나 만료된 신청을 복원하지 않는다. 크론 보류 중에는 조치 필요 상태를 정확한 시각에 모든 사람에게 통보한다고 약속할 수 없다.

기존 공개 경기는 새 최소 구성을 소급 적용해 자동 취소하지 않는다. 영향 목록을 만들고 운영자가 조건 제공 가능 여부를 확인한 뒤 기존 참가자에게 개별 안내한다. 새 작성·공개부터 검증을 적용하는 정책 버전이 필요하다.

## 4. R06 — 계약 역할·책임·신청 전 고지

### 코드와 현재 문구에서 확인한 공백

| 위치 | 확인한 내용 | 필요한 개선 |
| --- | --- | --- |
| [이용약관](../src/app/terms/page.tsx#L12) | 분쟁을 중재하지 않는다고 단정, 개인 부상·소지품은 각자 책임 | 서비스의 실제 업무와 법령상 책임을 분리. 시설 결함·과실까지 면책하는 표현 제거 검토 |
| 이용약관의 취소·환불 | 모든 참가자 취소를 100/50/0으로 읽을 수 있음 | 미확정 종료 전액 반환·초과분 반환과 확정 참가의 자발적 취소를 구분 |
| [신청 모달](../src/features/partner/partner-session-detail.tsx#L62) | 날짜·금액·계좌이체 및 자기소개 위주 | 계약 공급자·최소 진행 조건·기한·환불 규칙을 신청 전 간결하게 표시 |

| [개인정보 처리방침](../src/app/privacy/page.tsx#L12) | 일반 매칭의 정산 계좌 중심, 코트 환불 계좌·대조 이력·문의 전달 범위 불명확 | 참가자 본인·해당 운영자·담당자의 접근 범위와 처리 목적/보존 기준 구분 |

사용자 문제는 “돈을 보내기 전에는 조건을 못 봤고, 나중에 규칙이 달라졌다”는 분쟁이다. 핵심 조건을 신청 전에 짧게 보여주고 당시 내용을 남기는 기능은 현재 유료 코트 매칭에 필요하다. 긴 약관을 매번 입력하게 하는 방식은 필요하지 않다. 동의 체크 하나만 남기고 내용·버전을 저장하지 않는 대안은 조건 증명이 약하다.

### 법령 확인에서 도출한 검토 항목

- 전자상거래법 제20조의 **2026-07-21 시행본**은 통신판매중개 해당 시 당사자가 아니라는 고지, 사업자 신원정보 제공, 불만·분쟁 대응 조치를 다룬다. 직접 계좌이체라는 이유만으로 이러한 의무가 사라진다고 추론할 수 없다. Rally On의 실제 역할에 대한 법적 분류는 사업자 계약과 제공 업무를 확인한 뒤 판단해야 한다. [국가법령정보센터 제20조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0020&lsiSeq=282793&urlMode=lsScJoRltInfoR)
- 약관법 제7조는 사업자의 고의·중과실 책임 배제와 부당한 위험 전가 등 면책 조항을 제한한다. “개인 부상은 각자 책임”이라는 문구를 시설 결함이나 운영자 과실에까지 적용하는 결론을 내리지 않는다. [국가법령정보센터 제7조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0007&lsiSeq=260021&urlMode=lsScJoRltInfoR)
- 법제처의 체육시설 수강료 안내는 계약과 다른 용역, 시설 이용 불가, 신체 피해, 사업자/소비자 귀책을 구분한다. 이는 **사유를 나눠야 한다는 검토 근거**이며, 일회성 테니스 매칭 참가권에 수강료 산식을 그대로 적용할 근거는 아니다. 현재 100/50/0 규칙이 적법하다고 검증한 것도 아니다. [찾기쉬운 생활법령정보](https://www.easylaw.go.kr/CSP/CnpClsMain.laf?ccfNo=4&cciNo=1&cnpClsNo=3&csmSeq=631)

확인이 필요한 사실은 계약 공급자, 참가비에 포함된 시설/경기/현장 진행 범위, 사업자 표시 정보, 현장 연락 방법, 영수증 발급 주체, 사고 대응 및 보험, 실제 문의 담당자와 응답 시간이다. 제공되지 않은 사업자 정보나 연락처를 임의로 만들지 않는다. 일반 개인 매칭과 운영자 유료 코트 매칭에도 같은 법적 역할을 일괄 적용하지 않는다.

### 화면·API·데이터 변경안

신청 전 요약에는 운영 주체, 유형과 최소 구성, 코트/일시/이용 범위, 금액, 취소 사유별 반환 기준, 이체·확인 기한을 표시한다. 운영자 승인 방식에서는 실제 승인 시각에 기한이 확정되므로 신청 단계의 예상 기한과 승인 후 확정 기한을 구분하고 이체 전에 다시 보여준다.

서버가 정책 버전과 고지 내용을 결정하고 신청에 스냅샷을 저장한다. 브라우저가 계산한 환불액/기한을 신뢰하지 않는다. 새로운 불리한 조건으로 바뀌었으면 재확인 없이 승인/이체로 이어지지 않게 한다. R08의 자정 경계 취소 금액 변경 문제도 같은 방식으로 현재 금액을 다시 확인받되, 별도의 구현 단위로 테스트한다.

일반 매칭의 소개·카카오 길찾기·채팅·성별 정원 등은 이 검토에 포함하지 않는다. PG·외부 알림·새 크론도 추가하지 않는다.

## 5. 다음 작업을 작게 나누는 순서

1. **R04 거래 인계 정책 확정 → 구현:** 탈퇴 미리보기·제한 접근·담당 재배정과 권한/동시성 검증. 반환 기록을 살려 둔 첫 작업의 후속 단위다.
2. **R05 실제 경기 구성 정책 확정 → 구현:** 새 공개의 구성 검증, 진행 관문과 현재 제공 가능 여부 분리, 운영 사유 취소 연결. 기존 데이터 영향 목록을 먼저 확인한다.
3. **R06 계약 사실·법적 적용 확인 → 고지 정비:** 이미 확정된 미확정 전액/초과분 반환 안내부터 현재 로직과 맞추고, 공급 범위·환불율·책임은 확인된 내용만 약관과 스냅샷에 반영한다.

새 정책을 적용하기 전 정본과의 충돌을 해결해야 한다. 특히 `판정 후 무조건 유지 → 제공 불가 예외`, `계정 비활성 전면 차단 → 본인 거래 제한 접근`은 문구 변경만으로 처리할 수 없다. 각 단위가 여러 화면·권한·데이터에 걸치므로 디자인 수정과 동일한 일정으로 간주하지 않는다.
