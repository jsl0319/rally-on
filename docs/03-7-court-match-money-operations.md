# 코트 매칭 입금 예외·환불·문의 처리

2026-09-10 · `03-6` R01~R03의 첫 구현 단위. 정책 정본 `03-2`의 해당 절을 보완한다.

## 범위

사용자가 승인한 첫 작업은 실제 입금의 확인 지연부터 반환과 문의 해결까지 연결하는 것이다. 코트 운영자가 은행에서 직접 송금하는 구조를 유지하며 PG·외부 유료 의존성을 추가하지 않는다. 구현은 데이터 모델·API·참가자/운영자/내부 담당자 화면과 검증을 포함한다. 크론 실행 주기는 보류를 유지한다.

## 입금 기한 — 사용자 확정

- 진행 판정은 시작 3시간 전을 유지한다.
- 새 승인에는 운영자 대조 시간 30분을 별도로 둔다.
- 판정 전 이체 기한은 `min(승인 + 6시간, 시작 - 3시간 30분)`, 확인 기한은 `이체 기한 + 30분`이다.
- 판정 후 추가 모집은 시작 90분 전까지 받고, 이체는 시작 60분 전, 확인은 시작 30분 전까지 받는다.
- 이체 여유가 30분 미만이면 새 신청/승인을 받지 않는다. 판정 전의 이 구간에는 이미 신청한 사람의 입금 확인은 계속 가능하다.
- 기존 승인에 고지한 기한은 앞당기지 않는다. 새 확인 기한이 없는 이전 신청은 기존 `paymentDueAt`을 따른다.
- 참가자의 이체 알림은 확정이 아니다. 운영자가 통장을 대조한 수령 금액과 시각을 기록하며, 기한 후의 입금은 참가 확정에 사용하지 않는다.

## 금전 기록과 자리

- 실제 수령한 누적 금액과 대조 이력을 신청 상태와 별도로 저장한다. 철회/만료/전체 취소 뒤에도 운영자가 기록할 수 있다.
- 금액 정정에는 이전 금액·변경 금액·시각·담당자·사유를 남긴다. 재요청 식별자로 중복 저장을 막는다.
- 마지막 수령 시각과 참가비 충족 시각을 구분한다. 정상 입금 뒤의 초과 입금이 정시 납부 기록을 덮지 않게 하며, 대조 사유와 함께 두 시각을 정정할 수 있다.
- 정상 참가비와 초과 수령분을 구분하고, 새 입금 기록만으로 자리를 자동 복구하지 않는다.
- 미확정 종료(철회·거절·만료·전체 취소) 신청의 실제 수령액은 전액 반환한다. 초과·중복 수령은 초과분을 반환한다. 확정 참가자의 자발적 취소에는 기존 날짜별 100/50/0% 규칙을 유지한다.

## 환불 실행

- 참가자가 계좌를 저장하고 운영자가 처리 시작을 누르면 해당 금액과 계좌 버전을 환불 건에 고정한다.
- 처리 중에는 다른 송금 시작과 계좌 변경을 막는다. 서버의 Match 행 잠금을 공유한다.
- 은행 송금 후 처리 결과·시각·대조 메모를 기록한다. 실패는 사유와 함께 남겨 다시 처리할 수 있다.
- 완료를 잘못 표시했으면 확인 필요 상태로 옮긴다. 실제 송금 여부가 정리될 때까지 추가 송금은 막는다. 확인 결과와 수정 이유를 이력에 남긴다.
- 기존 완료 기록은 과거 기록으로 보존한다. 앱은 실제 은행 거래를 보증하거나 자동 송금하지 않는다.

## 문의

- 기존 1:1 문의에 담당자·답변·처리 상태·신청 참조를 연결한다. 회원은 본인 문의만 조회하고 추가 설명을 남긴다.
- 내부 담당자는 `INTERNAL_REVIEWER` 권한으로 접수 건을 맡고 답변하거나 코트 운영자에게 대조를 요청한다.
- 운영자에게는 담당자가 작성한 대조 요청과 해당 매칭의 신청 참조만 보여준다. 회원 문의 원문과 내부 논의를 자동 공개하지 않는다.
- 운영자는 자기 코트에 전달된 요청에만 답할 수 있다. 공개 답변과 운영자 대조 기록을 구분한다.
- 답변 완료와 해결 완료를 구분하며, 회원이 추가 문의하면 다시 검토 상태로 돌아간다.
- 법정 처리 기한이나 외부 알림을 새로 약속하지 않는다. 실제 담당자의 운영 시간·응답 목표는 별도 확정 사항이다.

## 이번에 바꾸지 않는 정책

확정 참가자의 자발적 취소 환불율, 진행 최소 구성, 판정 후 경기 유지, 탈퇴 후 처리 권한, 노쇼와 우천의 추가 보상은 별도 작업이다. 공유 DB 마이그레이션과 배포도 이 구현 검증과 분리한다.

## 구현·검증 기록 — 2026-09-11

첫 작업의 데이터 모델·서버·화면 구현과 로컬 검증을 완료했다. 기존 Claude 작업을 유지했고 새 프로덕션 의존성, 외부 송금 연동, 크론 변경은 추가하지 않았다.

- 운영자 매칭 상세 `/partner/court-matches/{matchId}`에서 실제 입금 대조, 누적 수령액 정정, 환불 시작·결과·확인 필요 처리와 이력을 조회한다. 신청 참조 링크는 해당 참가자 카드로 이동한다.
- 참가자는 기존 코트 매칭 상세에서 이체·확인 기한, 실제 반환 잔액, 계좌와 처리 상태를 확인한다. 송금 처리 중에는 계좌 변경을 막는다.
- 회원 문의 `/support/inquiry`, 내부 담당자 처리함 `/internal/support-inquiries`, 코트 운영자 대조 요청 `/partner/support-inquiries`를 연결했다. 담당자 배정, 답변, 대조 요청·회신, 재문의와 해결 처리를 지원한다.
- 미지급 반환액이나 처리 중·확인 필요 송금이 남으면 관련 문의를 해결 완료로 닫을 수 없다. 운영자에게는 회원 문의 원문과 회원용 답변을 공개하지 않는다.
- DB 행 잠금·고유 제약·버전 검증·재요청 식별자를 함께 사용한다. 두 운영 탭의 동시 송금 시작, 오래된 계좌/입금 버전, 결과 재요청과 다른 운영자의 접근을 검증했다.

검증은 공유 Neon 대신 전용 로컬 PostgreSQL에서 수행했다. `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `E2E_DATABASE_URL`을 모두 로컬로 지정하고 DB 테스트와 E2E는 순서대로 실행했다.

| 검증 | 결과 |
| --- | --- |
| `npm run check` | 린트·타입 검사·49개 파일 319개 테스트·프로덕션 빌드 통과 |
| 실제 DB 통합 테스트 | 위 319개에 포함된 39개 통과. 입금 예외·동시 환불·권한·기한 경계·문의 비공개 처리 포함 |

| 마지막 변경 재검증 | 미확정 입금 문의 → 대조 → 전액 반환 → 담당자 답변 → 해결 완료 흐름 재통과 후 전체 검사 재통과 |

DB 테스트 중 `pg`의 같은 연결에서 쿼리를 겹쳐 실행하는 방식에 대한 폐기 예정 경고가 출력됐으나 테스트 실패는 없었다. 새 송금 실행은 앱의 처리 기록을 검증한 것이며 실제 은행 송금 성공을 검증한 것은 아니다.

## 실제 환경 반영 전에 남은 일

1. 다음 두 마이그레이션은 전용 로컬 DB 검증 후, **2026-09-11 사용자 적용·배포 요청에 따라 운영 DB에도 적용했다.** Vercel 프로덕션 설정의 직접 연결을 사용했다. 기존 본문 없는 환불 완료 요청은 새 서버에서 허용하지 않는다.
   - `20260910030000_court_money_operations`
   - `20260910034500_court_fee_receipt_time`
2. 기존 확정 건은 참가비 수령액을, 기존 완료 환불은 과거 지급액을 보존한다. 과거 은행 입금 시각을 임의로 만들지 않으므로 실제 내역이 필요한 건은 운영자가 대조한다. 이전 승인 건에 고지한 기한도 앞당기지 않는다.
3. 담당자와 운영자가 모의 운영으로 입금 정정·송금 실패·완료 오표시·문의 재접수를 처리해 본다. 실제 운영 시간과 응답 목표는 아직 정하지 않았다.
4. 다음 정책 검토는 `03-6` R04~R06(탈퇴·중지 시 인계, 경기 제공 범위, 취소 조건과 계약 역할)이다. 나머지 검토 항목과 무접속 상태의 정시 판정 보장은 이번 완료 범위에 포함하지 않는다. **크론 작업은 사용자 재개 요청 전까지 계속 보류한다.**

## 운영 반영 기록 — 2026-09-11

- 사용자가 DB 적용·배포·커밋·푸시와 main 반영을 요청했다. 원격 main은 작업 기준 `4d98a82`와 같아 충돌이 없었다.
- 운영 PostgreSQL 18.6의 적용 전 백업을 git 제외 경로 `.vercel/backups/20260911-before-money-operations.dump`에 저장했다(파일 권한 600). 백업은 개인정보를 포함하므로 저장소나 배포 산출물에 넣지 않는다.
- 백업을 별도 로컬 DB `rally_money_rehearsal_20260911`에 복원해 두 마이그레이션을 다시 검증했다. 로컬 PostgreSQL 17 복원 시 18 전용 `SET transaction_timeout` 한 줄만 복원용 SQL에서 제외했으며, 운영 스키마나 마이그레이션 파일은 변경하지 않았다.
- 운영 적용 전후 회원 14명·매칭 23개·신청 4개·문의 0개가 유지됐다. 기존 확정 신청 1건의 수령액 보완과 두 마이그레이션의 성공 기록을 확인했다.
- DB 백업으로 되돌리면 이후 발생한 거래가 사라질 수 있으므로 자동 전체 복원은 하지 않는다. 문제 발생 시 새 금전 작업의 영향을 확인하고 서버 수정 또는 필요한 데이터 정정을 우선 검토한다. 이전 앱에는 새 환불 잠금 규칙이 없으므로 앱 롤백도 단독으로 안전하다고 가정하지 않는다.
- main 커밋·푸시와 기존 Vercel Git 연동 배포를 진행한다. 배포 결과와 다음 정책 검토는 후속 기록으로 남긴다. 크론 설정은 그대로 유지한다.
