# 탈퇴 이후 코트 거래 정리와 업무 인계

작성일: 2026-09-11 · 대상: `03-8` R04 · 사용자 권장안 승인 후 구현

## 1. 적용 범위

탈퇴하면 새 참가·모집 권한을 종료하면서, 이미 보낸 돈의 반환과 문의는 계속 처리한다. 일반 인증을 다시 열지 않고 기존 카카오 계정 인증으로 본인 거래만 접근한다. 신규 외부 인증·PG·자동 송금·크론은 추가하지 않는다.

사용자가 승인한 권장안은 탈퇴 허용과 제한 거래 접근, 운영자·담당자의 잔여 업무 인계다. 시작 전 코트 신청은 탈퇴 미리보기에서 취소 및 예상 반환액을 확인한 뒤 탈퇴와 같은 트랜잭션으로 취소한다. 기존 확정 참가의 날짜별 환불율 자체는 바꾸지 않는다. 시작한 경기와 일반 매칭의 신청·취소 정책은 이 단위에서 변경하지 않는다. 일반 매칭의 참가 취소·다시 모집 등 클로드의 작업은 보존한다.

## 2. 사용자 흐름

1. `마이 → 회원 탈퇴`에서 코트 신청별 취소 여부·예상 반환 잔액, 미확인 입금 가능 건, 송금 중 여부, 운영 거래 및 담당 업무 수를 확인한다.
2. 서버가 계산한 미리보기 토큰과 최신 상태를 비교한다. 신청·입금·환불 계좌 버전이나 날짜별 반환액 등이 바뀌면 409를 반환하고 재확인을 요구한다. 자정 경계의 계산·취소에는 같은 판단 시각을 사용한다.
3. 시작 전 PENDING/ACCEPTED는 WITHDRAWN, CONFIRMED는 CANCELLED로 바꾸고 기존 자리·채팅 멤버십 정리 함수를 재사용한다. 미확정 종료 건의 실제 수령액은 전액 반환 대상이며, 송금 처리 중 금액·계좌는 변경하지 않는다.
4. User를 WITHDRAWN으로 바꾸고 직접 업로드한 프로필 사진·카카오 사진 URL 및 알림 수신을 정리한다. 기존 거래와 원래 호스트 ID는 보존한다. 같은 카카오 재로그인은 신규 계정 생성·프로필 사진 재수집·재가입으로 취급하지 않는다.
5. `/account/transactions`에서 본인 코트 거래의 반환액·송금 상태·환불 계좌와 문의를 확인한다. 로그인·홈·보호된 일반 페이지는 비활성 회원을 이 경로로 보낸다. 일반 프로필/신청/운영 API는 여전히 403이다.

반환 잔액이 0원이어도 아직 대조되지 않은 입금에 관해 문의할 수 있다. 제한 접근은 본인 거래 기록이 존재하는 범위에만 적용한다. 기록이 없으면 빈 화면과 로그아웃을 제공한다. 보존 기간·파기 근거와 실제 운영 담당 체계는 공개 출시 전 별도 확정해야 하며, 이 구현을 전체 프로필·채팅·계좌의 무기한 보관 승인으로 해석하지 않는다.

## 3. 운영자와 내부 담당자

- User가 비활성이면 코트 매칭 공개 목록과 신규 신청·승인·참가 확정을 막는다. 기존 참가자의 상세에는 운영 중단을 표시하고 추가 이체 안내·입금 폼을 숨긴다. 공개 승인 중지와 계정 탈퇴는 다른 상태이며, 계정이 ACTIVE인 공개 중지 운영자의 기존 반환 권한은 유지한다.
- `/internal/support-inquiries`에서 `/internal/court-handoffs`로 이동한다. 비활성 운영자의 과거·현재 코트 거래를 50건 단위로 조회한다. 과거 경기도 늦은 입금 대조를 위해 남는다. 금융 상세는 해당 거래를 인계받은 활성 INTERNAL_REVIEWER만 조회한다.
- 담당자가 인계 사유와 확인 근거를 남기고 건을 맡는다. 다른 활성 내부 담당자의 건을 가져올 수 없다. 계정이 비활성이거나 내부 담당 역할이 종료된 경우에는 재배정할 수 있다. 본인이 운영했거나 신청한 거래는 스스로 처리하지 못한다.
- Match.hostUserId는 그대로다. `CourtTransactionHandoff`는 담당자와 버전, `CourtTransactionHandoffEvent`는 이전 담당자·실제 기록자·요청 번호·근거·시각을 남긴다. 입금·환불 원장에도 실제 처리자의 User ID를 남긴다.
- 담당자는 지정된 내부 API로 수령 누적액 정정·환불 처리 시작·송금 결과만 기록한다. 참가 승인이나 기한 우회, 자리 복원은 허용하지 않는다. 환불 계좌 입력은 본인에게만 허용한다. 기존 PROCESSING/REVIEW 송금은 그대로 인계하며 미송금으로 임의 변경하거나 이중 처리하지 않는다.
- 시작 전 경기의 제공 불가를 확인하면 사유와 함께 취소할 수 있다. 현재 PENDING/ACCEPTED/CONFIRMED 신청을 CANCELLED로 바꾸고 실제 수령액 전액을 반환 대상으로 남긴다. 과거 자발 취소자의 금액·사유는 덮어쓰지 않는다. 먼저 취소한 참가자에게도 사후 추가 반환할지에 관한 정책은 R05/R06에서 별도로 검토한다.
- 문의 재배정에는 `SupportInquiryMessage.previousAssigneeUserId/nextAssigneeUserId`와 작성자·시각을 남긴다. 비활성 운영자에게 새 대조 요청을 보내고 무한 대기시키지 않고 거래 인계 화면으로 안내한다.

## 4. 동시성·권한 경계

순서는 `계정 거래 공유 잠금 → Match 행 잠금 또는 문의 행 잠금`이다. 코트 신청·승인·입금 확정·공개, 금융 변경, 문의 처리 및 내부 인계는 PostgreSQL 공유 advisory transaction lock `(72604, 1)`을 먼저 얻는다. 서로 다른 매칭은 계속 동시에 처리할 수 있다. 드문 탈퇴와 탈퇴 미리보기만 같은 키의 배타 잠금을 얻고 관련 Match를 ID 순으로 잠근다. 그 안에서 User 상태를 다시 확인하므로 인증 직후 탈퇴와 신청이 경합해도 비활성 계정의 새 자리가 생기지 않는다.

크론/기한 보정은 기존 Match 잠금을 사용한다. 탈퇴 토큰 재검증 실패 때도 기한 보정 결과는 커밋하고, 실제 탈퇴·선택한 참가 취소는 수행하지 않는다. 외부 객체 삭제는 DB 트랜잭션 밖에서 한다. 신규 자동 스케줄이나 현재 일일 크론 설정은 변경하지 않는다.

## 5. 데이터·API

마이그레이션: `20260911070000_account_transaction_continuity`

- `court_transaction_handoffs`: Match당 1개, 담당자 참조, version.
- `court_transaction_handoff_events`: 실제 기록자·이전 담당자·요청 UUID·근거·시각, `(handoffId, clientRequestId)` 유일.
- `support_inquiry_messages`: 이전·이후 담당자 UUID 추가.
- 기존 입금·환불 금액이나 송금 상태를 소급 변경하는 데이터 migration은 없다.

| 경로 | 접근·역할 |
| --- | --- |
| GET `/api/v1/me/withdrawal` | 활성 본인의 탈퇴 미리보기 |
| POST `/api/v1/me/withdrawal` | `{token}` 재검증 후 탈퇴. 이미 탈퇴된 동일 계정 재요청은 같은 종료 상태 반환 |
| GET `/api/v1/me/transactions` | 인증된 본인의 코트 거래만. 비활성 계정 허용 |
| GET/POST `/api/v1/me/transactions/inquiries` | 본인 기존 코트 거래 문의만. 무관한 매칭 ID·거래 없는 새 문의 거절 |
| POST `/api/v1/me/transactions/inquiries/{id}` | 본인의 코트 거래 문의에 추가 답변만 |
| PUT `/api/v1/court-match-applications/{id}/refund-account` | 인증된 신청자 본인만. 비활성 계정 허용, 송금 중 잠금 유지 |
| GET `/api/internal/court-handoffs` | 활성 내부 담당자 목록, cursor 페이징 |
| GET/POST `/api/internal/court-handoffs/{matchId}` | 배정된 담당자의 금융 상세 / 인계 요청 `{expectedVersion,clientRequestId,note}` |
| POST `/api/internal/court-handoffs/{matchId}/cancel` | 배정된 담당자의 제공 불가 취소. 동일 요청 구조 |
| POST `/api/internal/court-handoff-applications/{id}/receipt`, `/refund/start`, `/refund` | 배정된 담당자만. R01 금전 입력·버전·재요청 계약 재사용 |

일반 금융 API에서 클라이언트가 인계 플래그를 보내도 대리 권한은 생기지 않는다. 내부 경로가 명시적으로 내부 접근 모드를 전달하고, 서비스는 DB의 최신 역할·계정 상태·배정을 다시 검사한다. 내부 상세에 테니스 프로필과 신청 메시지는 공개하지 않는다.

## 6. 검증과 현재 배포 상태

- 전용 로컬 `tennis_mate_e2e` DB에 migration 적용 완료. 운영 DB에는 이번 migration을 적용하지 않았다.
- 전체 단위·DB 테스트 51개 파일 341건 통과. 코트 DB 50건, 일반 매칭 DB 7건을 포함하며 공유 테스트 DB 초기화 충돌을 막기 위해 파일을 순차 실행했다. 탈퇴/권한 종료 재배정과 자정 경계의 반환액 재확인도 검증했다.
- 전체 모바일 E2E 11건 통과(새 거래 연속성 2건 + 기존 9건). 린트·타입·Prisma 스키마 검증과 프로덕션 빌드 모두 통과.
- 모바일은 390×844에서 실제 브라우저로 확인: 탈퇴 미리보기 → 제한 페이지 → 본인 환불 계좌/문의, 운영자 탈퇴 → 내부 인계 → 제공 불가 취소 → 늦은 입금 기록 → 반환 완료.
- 기존 클로드 커밋과 일반 매칭/픽스처/재모집 테스트의 미커밋 변경은 수정하지 않았다. 이 작업의 E2E는 별도 `account-continuity.spec.ts`에 추가했다.
- R05 실제 경기 구성, R06 법적 역할·계약 조건 스냅샷은 이 단위의 완료 항목이 아니다. 크론은 보류 상태다.

검증 로그는 `/tmp/rally-r04-final-tests.log`, `/tmp/rally-r04-final-e2e.log`, `/tmp/rally-r04-final-build.log`에 남겼다. 모바일 확인 이미지는 `/tmp/rally-r04-account-mobile.png`, `/tmp/rally-r04-handoff-mobile.png`다. 이 단위는 로컬 구현·검증 상태이며 커밋·푸시·운영 DB 적용·배포는 아직 하지 않았다. 배포할 때는 운영 백업과 migration 검증을 거쳐야 하며 클로드의 미커밋 변경을 임의 포함하지 않는다.
