# 금융 최종 대조와 보존 사유 기록

작성일: 2026-10-10. [03-19](03-19-personal-data-retention-policy-proposal.md)의 승인된 계좌 원문 정리 기준을 위한 후속 구현. 실제 파기·운영 DB 변경·배포는 별도 단계다.

## 목적과 범위

잔액 0원만으로 은행 대조 완료를 판단하는 문제를 막는다. 기존 운영자의 입금·환불 패널과 인계 담당자 패널에서 최종 대조 사실과 필요한 원문 보존 사유를 기록한다. 외부 시스템·새 담당 권한·크론을 추가하지 않는다. 단순한 완료 체크만 저장하면 이후 늦은 입금과 문의를 놓치므로 확인 당시 상태의 지문을 함께 저장한다.

## 동작과 권한

- 기존 금융 업무와 동일하게 활성 해당 코트 운영자 또는 배정된 활성 인계 담당자만 조회·기록한다. 본인 참가 신청은 직접 검토할 수 없다. 일반 참가자와 미배정 내부 담당자는 접근할 수 없다.
- `RECONCILE`: 참가 업무 종료, 실제 누적 수령액과 최신 수령 기록 일치, 미확인 입금·반환 잔액·진행 송금·재확인·진행 중 문의가 없을 때 담당자의 명시적인 은행 대조 확인을 저장한다. 기존 확정 시각에서 추정한 수령액이나 과거 환불 표시를 자동 승인하지 않는다.
- 확인 기록에는 담당자·기록 시각·거래 상태 지문만 저장한다. 계좌·예금주·입금자명·문의 원문을 복사하지 않는다. 상태 지문에는 신청/매칭 상태, 입금 알림 등을 반영하는 신청 갱신 시각, 수령 버전, 환불 계좌 버전, 송금 시도 및 관련 문의의 버전·갱신 시각가 포함된다.
- 늦은 입금·환불 결과 변경·계좌 변경·문의 접수/재개 등으로 지문이 달라지면 기존 기록은 이력으로 남고 ‘재대조 필요’로 표시한다. 새 기록은 이전 대조의 시각을 덮어쓰지 않는다.
- `HOLD`: 신청 입금자명, 현재 환불 계좌, 과거 송금 계좌 복사본, 해당 매칭 입금 계좌 중 필요한 범위를 고르고 사유·업무 참조·재검토일을 남긴다. 범위는 해당 신청과 연결된 기록으로 제한한다. 공용 Court 기본 계좌와 다른 참가자의 계좌에는 적용하지 않는다.
- `RELEASE_HOLD`: 보존 필요가 끝난 근거를 남겨 해당 보존 건 하나만 해제한다. 재검토일 경과는 자동 해제가 아니며, 해제 자체도 파기 승인이나 법정 보존 종료 판정이 아니다.
- 보존 사유 기록은 필요한 원문을 지키는 운영 기록이다. 담당자의 은행 대조 확인을 별도 법정 보존 검토 완료로 해석하지 않는다. 이번 구현에는 ‘법적 보존 사유 없음’ 승인이나 자동 삭제 버튼이 없다.

## 데이터와 API

`CourtFinancialReview`에 신청·처리자·중복 요청 키, 동작, 입력 지문, 거래 상태 지문, 보존 범위·사유·업무 참조·재검토일, 해제 대상, 작성 시각을 기록한다. 기존 거래 원문은 변경하지 않는다. 이전 기록 수정·삭제 API는 제공하지 않는다. 해제는 대상 신청과 동일한 보존 기록만 참조하며 이미 해제된 건은 다시 해제할 수 없다.

`GET/POST /api/v1/court-match-applications/{applicationId}/financial-review` 및 인계용 `/api/internal/court-handoff-applications/{applicationId}/financial-review`를 제공한다. 인증과 기존 금융 권한을 확인하고 응답은 `private, no-store`로 전달한다. POST는 `clientRequestId`, 조회 시 받은 `expectedFingerprint`를 요구한다. 동일 요청의 재전송은 같은 결과를 돌려주며 다른 내용은 충돌로 거절한다. 상태가 바뀐 화면에서의 저장도 거절한다.

계정 거래 잠금 → 매칭 잠금 순서를 유지한다. 보존/해제 기록도 지문에 포함해 동시에 열린 패널에서 오래된 상태로 처리하지 않도록 한다. 향후 실제 삭제에는 문의 생성 등 모든 관련 쓰기 경로와 파기 경로의 동시성 검토가 추가로 필요하다.

## 시간대 검증

설치된 Prisma 어댑터는 날짜를 UTC 기준으로 변환한다. 공통 어댑터 생성 함수에서 접속 옵션의 마지막에 `timezone=UTC`를 명시해 앱·시드·검증 코드의 연결마다 적용한다. 기존 접속 옵션은 유지한다. 저장된 과거 시각을 일괄 보정하지 않는다.

2026-10-10 Vercel의 운영 `DATABASE_URL` 한 항목만 메모리에서 읽어 **설정만 조회**했다. 기존 연결 `GMT`, UTC 명시 연결 `UTC` 모두 성공했다. 운영 데이터 행은 읽거나 수정하지 않았다. 전체 환경변수를 파일로 받는 시도는 자동 승인 검토에서 거절돼 실행되지 않았으며, 개별 변수 조회로 범위를 좁혀 확인을 마쳤다.

관련 보고: [Prisma 공식 저장소의 시간대 문제](https://github.com/prisma/orm/issues/28629). 현재 버전의 로컬 재현과 운영 연결 설정을 판단 근거로 삼으며, 과거 운영 데이터 전체의 정확성을 검증한 것으로 해석하지 않는다.

## 완료 조건

정상 완료, 진행 중 송금, 미확인 입금, 지문 변경, 문의 재개, 과거 데이터, 보존 기한 경과·해제, 권한 상실·다른 운영자·자기 신청, 중복·동시 요청을 로컬 DB에서 검증한다. UI는 작은 화면에서 조회·기록·실패 안내를 확인한다. 운영 마이그레이션·배포·개인정보 삭제·크론 변경은 하지 않는다.


## 점검 결과와 후속 조건

읽기 전용 점검은 대조 상태가 현재 거래와 일치하면 `FINAL_RECONCILIATION_UNRECORDED` 대신 대조 근거가 있는 것으로 분류한다. 이후 거래·문의 변경은 `FINAL_RECONCILIATION_STALE`, 선택 범위의 활성 보존은 `PRESERVATION_HOLD`, 재검토일 경과는 `PRESERVATION_REVIEW_OVERDUE`다. 신청 원문 보존과 매칭 공용 계좌 보존을 구분한다. 집계는 신청/매칭 단위이며 개별 필드 삭제 대상 목록이 아니다. 모든 경우 별도 보존 근거 검토(`RETENTION_BASIS_UNASSESSED`)와 `deletionEnabled: false`는 유지한다.

실제 삭제 전에는 최소 거래 기록(은행·끝 네 자리 등), 파기 후 늦은 환불 계좌 재입력, 과거 송금 복사본·메모 원문, 보존 검토 책임·기준, 문의 생성과 파기 동시성 및 복구 방지를 추가로 완결해야 한다. 아직 결정되지 않은 채팅 보관 기간은 이번 기능으로 확정하지 않는다.


## 검증 결과 (2026-10-10)

- 격리된 PostgreSQL 17 DB에 34개 마이그레이션 적용 성공. 운영 DB 마이그레이션은 실행하지 않음.
- 전체 **60개 파일·468개 단위/DB 테스트 통과**, 린트·타입 검사·Prisma 스키마 검증·프로덕션 빌드 통과.
- 새 대조/보존 검증: 명시적 은행 확인, 수령 근거 누락, 최근 입금 알림, 송금 진행, 참가 업무 미종료, 오래된 화면, 문의 재개, 보존 기한 경과 유지, 범위별 집계, 다른 신청 보존 해제 차단, 중복·동시 요청, 비활성 운영자·배정·담당자 권한 상실·본인 신청 차단.
- DB 시간대가 Asia/Seoul이어도 공통 Prisma 연결은 UTC이며, 명시한 다른 접속 옵션은 유지됨. 날짜 생성 후 별도 pg 연결에서 같은 절대 시각으로 읽히는 회귀 테스트 통과.
- **390px 모바일 Playwright 1개 흐름 통과**. 운영자 화면에서 조회 → 대조 확인 → 보존 등록 → 해제 → 거래 변경 후 재대조 표시를 확인. 503 응답 후 재시도, 비로그인 401, 잘못된 입력 422, private/no-store 응답, 원문 유지와 DB 이력 3건, 가로 넘침 없음·페이지 실행 오류 없음 확인. 화면 캡처도 검토함.

| 경계 | 확인 근거 |
| --- | --- |
| 운영자 화면 → API | 버튼·폼으로 실제 GET/POST 실행, 실패 안내 후 재시도 성공 |
| API → DB | 독립 로컬 DB에 대조·보존·해제 3개 이력, 원문 불변 확인 |
| DB → 화면 | 대조 완료·보존 중·해제·재대조 필요 상태 표시 확인 |
| 권한·동시성 | 운영자/배정 담당자 외 차단, 동일 지문 동시 요청 1건 반영 |

기존 Prisma/pg 경로에서 동일 연결의 동시 쿼리에 관한 pg 차기 버전 경고가 계속 출력되지만 테스트 실패는 없었다. 이 경고 정리와 실제 개인정보 파기, 운영 반영은 이번 완료 범위에 포함하지 않는다. 크론 설정은 변경하지 않았다.
