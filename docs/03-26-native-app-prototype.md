# 설치형 앱 1차 검증

2026-10-10. 사용자 승인: Android·iOS 앱 전환 구조, 카카오 로그인·복귀·유지, 목록·상세·뒤로가기·키보드 검증. 두 플랫폼의 실제 휴대전화가 있다.

## 현재 상태 — 인수인계 검토 (2026-10-14)

- 사용자가 마무리할 Claude 작업을 `설치형 앱·푸시 관련 작업`으로 확인했다. 시제품 소스와 푸시 안내는 이미 main에 반영되어 있으며, 별도 미반영 변경을 합치거나 기존 구현을 교체할 필요는 없었다.
- `mobile/prototype` 검사 17개가 모두 통과했다. 실제 Swift 지도 URL 변환 검사도 포함한다. `doctor`의 Node·Xcode 선택·Android Studio·SDK 36 점검 4개가 통과했다. 이번에 Xcode/Android 전체 빌드나 기기 재설치를 새로 수행했다는 뜻은 아니다.
- 생성된 iOS 프로젝트의 설정·SceneDelegate·LaunchScreen·로고 에셋을 버전 관리 원본과 대조해 일치함을 확인했다. 카카오 callback을 같은 origin에 유지하는 시작 주소 설정, 로컬 시작 파일 누락 방지, 기존 Scene 창 재사용, 제한된 지도 링크 처리는 유지한다.
- iPhone의 로그인·앱 복귀·재실행·지도·오프라인 복구는 아래 사용자 확인 결과를 유지한다. 이후 사용자 확인으로 로그인 화면의 검은 틈과 운영자 등록의 날짜 입력·하단 버튼도 정상이다. 관리자 메뉴, 공지 초안·공개·수정·숨김·삭제, 로그아웃 취소 시 스크롤 유지도 실기기에서 정상이라고 확인했다. 회원 탈퇴 버튼 정렬은 `824d370` 운영 반영 후 사용자가 iPhone에서 정상이라고 확인했다. 실제 회원 탈퇴를 실행한 결과는 아니다.
- **외부 푸시는 미구현이다.** 푸시 플러그인·권한 요청·기기 토큰 저장·서버 발송·알림 클릭 이동이 없다. 로컬 알림이나 인앱 알림을 외부 푸시로 간주하지 않는다. 다음 단계는 [03-25 최신 준비 상태](03-25-web-push-pilot-proposal.md#2026-10-14-인수인계-검토와-다음-작업)를 따른다.
- 사용자는 유료 Apple Developer Program 없이 무료 Personal Team만 사용 중이라고 확인했다. 가입·결제·푸시 자격 증명 생성은 진행하지 않았다. Android 실기기는 사용자 결정대로 보류한다.

아래 날짜별 기록은 당시 결과다. 과거의 `미해결`·`대기` 문구를 현재 상태로 읽지 않으며, 최신 상태는 이 절과 완료 기준 표를 우선한다.

## 앱 아이콘·이름 확정 (2026-10-14)

- 사용자는 B 시안을 서비스 아이콘으로 확정하고, 설치형 앱 이름을 `랠리온 검증`으로 변경·배포·iPhone 반영하도록 요청했다. 직전 검토한 **B 수정안(B2: R 안쪽 빈 공간의 테니스공)**을 최종 원본으로 적용한다.
- 서비스 원본은 `public/images/brand/app-icon.svg`이며, 브라우저 favicon/SVG·iPhone 홈 화면 웹 아이콘·iOS AppIcon을 같은 원본에서 생성한다. 기존 Rally On 워드마크와 로그인 화면은 유지한다.
- A·B 원안·B2·C와 비교 이미지, Mobbin 조사 근거는 `docs/design/app-icon-20261014/`에 보관한다. `selection.json`에 확정 원본을 명시해 추후 원안과 혼동하지 않는다.
- `prepare:ios`가 이름과 아이콘도 재현하도록 변경한다. 기존 `dev.rallyon.prototype` 식별자·서명 팀·서버 주소를 유지하므로 다른 앱을 새로 만드는 작업이 아니다. 기존 네이티브 파일을 별도로 수정한 경우 자동 덮어쓰지 않는다.
- 운영 웹은 기존 검증 후 승격 절차를 따르며, iPhone 홈 화면 아이콘·이름은 별도 서명 빌드와 재설치로 반영한다. 빌드·설치·실제 홈 화면 확인 결과는 각각 구분해 기록한다. Android 실기기 반영은 보류 상태다.
- 검증: 웹 lint·typecheck·단위 테스트 442개·프로덕션 빌드 통과(조건부 DB 테스트 132개 skipped). 시제품 검사 19개 통과. iOS 서명 빌드·서명 검증을 통과하고 기존 iPhone 앱 위에 업데이트 설치·실행했다. 빌드의 표시 이름은 `랠리온 검증`, 아이콘은 선택 원본과 동일한 불투명 1024px 이미지다. 실제 홈 화면의 모양·이름에 대한 최종 육안 확인은 사용자 확인 전까지 미검증이다. 새 DB 마이그레이션은 없다.

## 목적과 범위

기존 화면을 다시 만드는 비용을 들이기 전에 모바일 WebView에서 재사용 가능한지 확인한다. 매칭 탐색·신청이라는 핵심 흐름을 설치형 앱으로 연결하기 위한 선행 검증이다. `mobile/prototype`을 독립된 개발 패키지로 두며, 기존 Next 서버·인증·DB·배포 설정은 바꾸지 않는다. 새 Capacitor 의존성은 이 검증 패키지에만 설치한다. 더 단순한 대안인 홈 화면 웹앱은 스토어 설치라는 목표를 충족하지 않으므로 이번 대상에서 제외한다.

## 이번 실험의 의미

- Capacitor의 개발용 `server.url`을 이용해 기존 서버 렌더링 화면을 실행한다. Next의 서버 인증·DB 조회를 정적 내보내기로 바꾸지 않는다.
- 이는 **화면과 기존 웹 로그인 호환성을 측정하는 개발 시제품**이다. 스토어 제출 구조가 확정됐거나 외부 브라우저와 앱 간 인증 연결이 구현됐다는 의미가 아니다.
- 현재 Auth.js는 카카오 REST OAuth와 서버 세션 쿠키를 사용한다. 같은 WebView 안에서 돌아오는 경우와 카카오톡/시스템 브라우저로 나간 경우를 따로 확인한다. 브라우저 쿠키가 WebView에 공유된다고 가정하지 않는다.
- 외부 브라우저에서 로그인이 끝나 앱에 반영되지 않으면 그 결과를 실패로 기록한다. 쿠키 복사나 URL에 세션 토큰을 붙여 우회하지 않는다. 이후 별도 검증 단위로 외부 인증 세션과 일회성·만료·요청자 검증을 갖춘 인증 전달을 설계한다.
- OAuth 관련 WebView 이동 허용은 `kauth.kakao.com`, `accounts.kakao.com` 두 호스트만 개발 실험에 사용한다. 광범위한 도메인 허용이나 민감한 네이티브 기능 플러그인을 추가하지 않는다. 다른 링크는 기본 외부 브라우저 동작을 확인한다.
- 기기에서 인증해도 운영 데이터 변경을 자동 실행하지 않는다. 실제 계정 로그인은 사용자가 직접 수행한다. 목록/상세 조회 외 신청·입금·취소 버튼은 이 검증의 대상이 아니다.

- 최초 `doctor`에서 양쪽 개발 도구 미준비를 확인한 뒤 사용자의 요청으로 설치를 지원했다. 실제 시스템 환경의 최종 `doctor`에서 Node·Xcode 선택·Android Studio·SDK 36 네 항목 모두 통과했다.
- Android Studio의 기본 JDK 25는 Gradle 8.14.3 실행 범위를 벗어나므로 Homebrew OpenJDK 21로 `assembleDebug`를 실행했다. `BUILD SUCCESSFUL`, 93개 작업 완료, Debug APK 생성(약 3.9MB)을 확인했다. IDE에서도 안내된 `Use JVM 21`을 선택해 별도 JDK 다운로드·동기화를 진행했다. 전역 Java 기본값은 변경하지 않았다.
- Android 빌드에서 Capacitor 기본 `flatDir` 경고와 SDK XML 버전 경고가 있었으나 컴파일·패키징은 완료됐다. 시제품 설정 검사 11개도 재통과했다. APK 생성은 실제 기기 인증 검증을 의미하지 않는다.
- Xcode에서 SPM의 Capacitor 8.5.3 의존성을 받고 `generic/platform=iOS Simulator`, Debug, `CODE_SIGNING_ALLOWED=NO`로 `BUILD SUCCEEDED`를 확인했다. 로컬 결과는 `/tmp/rally-on-native-ios-build/Build/Products/Debug-iphonesimulator/App.app`이다. 실제 iPhone 서명·설치 성공을 의미하지 않는다. 외부 에이전트 접근은 이번 빌드에 필요하지 않아 초기 설정에서 `Never`를 선택했다.
- 설치 직후 Xcode Run으로 iPhone 18 Pro / iOS 27.0에서 프로세스 실행까지 확인했지만 화면이 검게 표시되어 **화면 표시 검증은 실패/미해결**이다. 시뮬레이터 재시작 후 홈 화면은 정상으로 돌아왔고 앱 재실행에서는 다시 검은 화면이었다. 운영 `/login`은 Mac의 읽기 전용 요청에 HTTP 200을 반환했고, 앱 오류 로그 조회에는 원인을 특정할 오류가 없었다. 다음 작업은 실제 기기 테스트 전에 iOS WebView/Scene 초기화·시뮬레이터 내 네트워크를 분리해 원인을 확인하는 것이다. 설치 완료와 앱 정상 동작을 혼동하지 않는다.
- 현재 로컬 시제품 대상은 기존 운영 HTTPS 로그인 화면이다. 서버의 인증·거래 API를 수정/배포하거나 실제 계정 로그인을 대신 수행하지 않았다.

## 2026-10-10 초기 화면 후속 점검

- 기존 빌드를 변경하지 않은 상태에서도 시간이 지난 뒤 로그인 화면이 표시됐다. 재실행 시 검은 화면을 재현했고, 디버거에서 활성 Scene·창·WKWebView는 존재하지만 초기 `/login` 로딩 진행률 0.1, `isLoading=true`, 콘텐츠 크기 0을 확인했다. 로그에는 WebKit 네트워크/GPU/콘텐츠 프로세스 시작 지연과 응답 없음 기록이 있었다. 서버 응답 성공만으로 기기 WebView 상태를 판단할 수 없으며, 지연의 근본 원인을 서버 장애나 Scene 누락으로 단정하지 않는다.
- Capacitor 생성 템플릿은 storyboard 창과 별도로 SceneDelegate에서 창/브리지를 다시 만들고 있었다. UIKit이 이미 만든 창을 재사용하도록 수정했다. [Apple의 storyboard Scene 설명](https://developer.apple.com/documentation/uikit/supporting-multiple-windows-on-ipad)을 확인했다.

4. iPhone 검증 완료 후 Android 데이터 케이블·USB 디버깅 승인을 확인한다. `adb devices -l`이 `device` 상태일 때 기존 Debug APK를 설치하고 같은 항목을 확인한다. `unauthorized`라면 기기에서 사용자가 직접 승인한다.

## 2026-10-10 iPhone 로그인 callback 수정

- 사용자가 개발자 신뢰 처리 후 앱 진입 성공을 보고했다. 이후 로그인 시 외부 브라우저에 Auth.js `Server error`가 표시된 화면을 제공했다. 목록·로그인 유지 성공을 의미하지 않는다.
- 운영 Vercel의 `/api/auth/callback/kakao` 로그에서 `InvalidCheck: pkceCodeVerifier value could not be parsed`를 확인했다. Auth.js 검증 단계의 실패이며 DB 오류나 카카오 키 누락으로 단정하지 않는다.
- 시제품의 `server.url`이 `https://…/login`으로 설정돼 있었다. 설치된 Capacitor 8.5.3 iOS `WebViewDelegationHandler`는 앱 URL 접두어로 내부 이동을 판정하므로 같은 호스트의 `/api/auth/callback/kakao`도 외부 이동으로 분류했다. 앱 WebView에서 시작한 로그인과 외부 브라우저의 쿠키 저장소가 분리되는 원인이 된다.
- `server.url`은 origin + `/`, 시작 화면은 `server.appStartPath`로 분리했다. 오프라인 복구 링크와 prepare의 설정 검증도 시작 경로를 반영한다. 같은 호스트의 callback·온보딩·상세 이동과 다른 호스트 경계를 확인하는 회귀 검사를 추가해 시제품 검사 14개가 통과했다.
- 기존 PKCE 검증·서버 인증 설정·DB·운영 배포는 변경하지 않았다. 외부 카카오톡에서 브라우저로 돌아오는 별도 흐름까지 해결됐다고 간주하지 않으며, 수정된 앱에서 사용자 로그인·앱 복귀를 다시 확인한다.
- 수정본의 실제 기기 서명 빌드 `BUILD SUCCEEDED`와 iPhone 덮어쓰기 설치 성공을 확인했다. 사용자에게 외부 오류 탭 대신 앱을 종료·재실행해 로그인을 새로 시작하도록 안내했다. 최종 로그인 결과는 대기 중이다. Android는 iPhone 검증 후 `prepare:android` 및 재빌드하여 같은 설정 수정을 반영해야 한다.

### 시작 직후 종료 회귀 수정

- 위 callback 수정본에서 사용자가 ‘잠깐 열렸다가 홈 화면으로 돌아감’을 보고했다. 연결 복구 후 `devicectl --console` 진단 실행에서 앱의 종료 코드 1을 확인했다.
- 설치된 Capacitor 8.5.3의 `CAPBridgeViewController.loadWebView()`는 원격 서버 설정 여부와 무관하게 `appStartFileURL`의 존재를 검사하고, 없으면 `fatalLoadError()` → `exit(1)`로 종료한다. `/login`을 `appStartPath`로 분리하면서 번들에 대응하는 `public/login` 파일을 생성하지 않은 것이 누락이었다. 컴파일·설치 성공만 확인하고 사용자에게 재시험을 요청한 검증 공백을 기록한다.
- `configure`에서 `/login` 시작용 로컬 복구 HTML도 생성하고, `prepare`에서 시작 파일이 없으면 플랫폼 복사 전에 중단하도록 수정했다. 임시 디렉터리에서 실제 configure 실행 → 파일 확인 → 파일 누락 시 prepare 차단을 확인하는 검사를 추가했다. 시제품 검사 15개와 시뮬레이터·실기기 서명 빌드가 통과했고, 양쪽 최종 앱 번들 안의 `public/login` 존재를 확인했다.
- 수정본을 시뮬레이터에서 실행해 네이티브 로딩 안내 이후 실제 로그인 화면과 카카오 시작 버튼 표시를 직접 확인했다. iPhone에도 업데이트 설치하고 진단 실행했으며 이전과 달리 즉시 종료되지 않고 프로세스가 유지됐다. 실기기 화면 표시와 카카오 로그인 완료는 사용자 재확인을 기다린다.
- 후속 사용자 확인: “잘 로그인 되고, 매칭 목록까지 잘 열리네.” iPhone의 수정본 실행·로그인·매칭 목록 도달은 사용자 확인으로 통과 처리한다. 인증 중 카카오톡/외부 브라우저 이동 여부, 취소 경로, 상세, 백그라운드 복귀·강제 종료 후 세션 유지 및 로그아웃은 아직 별도 검증이 필요하다. 다음은 복귀·재실행의 로그인 유지와 상세 조회를 확인하며, 실제 신청·거래 데이터는 변경하지 않는다.

## iPhone 복귀 및 지도 연결 후속 검증

- 사용자에게 홈 화면 복귀, 앱 완전 종료·재실행의 로그인 유지, 상세 조회 후 목록 복귀를 요청했고 세 항목 모두 확인했다는 답변을 받았다. 위 표에 반영했다.
- 사용자는 ‘이지테니스 둔촌점’ 매칭의 카카오맵 길찾기를 누르면 목적지 없이 지도 앱만 열린다고 보고했다. 기존 서버 코드는 이름·좌표를 가진 공식 `/link/to/` 웹 URL을 반환하며, 공개 연결 페이지는 `applink.map.kakao.com/route?…ep=…&en=…&by=car`로 이동하는 것을 확인했다. 실제 기기의 지도 앱 내부에서 어느 단계에 목적지가 유실되는지는 직접 관측하지 못했다.
- iOS 시제품에서는 앱 웹 화면에서 시작된 카카오맵 HTTPS `/link/to/{이름},{위도},{경도}` 이동만 가로채 공식 `kakaomap://route`에 목적지 좌표(`ep`)와 이름(`en`)을 직접 전달한다. 기존 웹 링크의 자동차 기본값(`by=car`)을 유지하고 출발지는 앱에서 수집하지 않는다. 이름·좌표 이외의 임의 쿼리는 받지 않고 호스트·프로토콜·좌표 범위를 검증한다.
- 앱을 열 수 없으면 기존 HTTPS 길찾기를 Safari 뷰로 표시한다. 카카오맵이 없는 사용자의 웹 대체 경로이며, 인증 쿠키 전달이나 광범위한 외부 앱 실행 API를 추가하지 않는다. 로그인·거래 서버 및 운영 배포는 변경하지 않는다.
- `KakaoMapLinks.swift`는 목적지 변환만 담당하고 macOS에서 실제 Swift 코드로 정상 좌표·한글/특수문자·다른 호스트·잘못된 좌표를 검사한다. `prepare:ios`는 SceneDelegate와 함께 하나의 생성 소스로 반영한다. 시제품 검사 16개 통과. 지도 앱 실제 목적지 표시와 앱 복귀는 수정본 설치 후 사용자 재검증이 필요하다.
- 근거: [카카오 iOS URL Scheme](https://apis.map.kakao.com/ios_v2/docs/getting-started/urlscheme/), [카카오 Web 길찾기](https://apis.map.kakao.com/web/guide/#routeurl). Android는 iPhone 완료 후 별도로 검증한다.
- 지도 수정본의 iPhone 서명·시뮬레이터 빌드가 통과했고, 시뮬레이터에서 기존 로그인 화면 표시를 확인했다. iPhone 업데이트 설치도 성공했다. 사용자에게 이지테니스 둔촌점의 목적지 표시와 Rally On 상세 복귀를 요청했으며 결과는 대기 중이다. 지도 앱 미설치 시 Safari 대체 경로는 구현했지만 실제 화면 검증은 아직 하지 않았다.
- 후속 사용자 답변 “확인했어”로 이지테니스 둔촌점 목적지 표시와 Rally On 상세 복귀를 확인했다. 지도 앱 설치 상태의 두 항목은 사용자 확인으로 통과 처리한다. 다음 실기기 확인은 로그아웃 후 보호 화면 접근 차단과 네트워크 끊김·복구다. 지도 미설치·인증 취소·키보드·안전 영역 등 아직 확인하지 않은 항목은 별도 미검증으로 유지한다.
- 사용자에게 로그아웃 후 완전 종료·재실행 시 로그인 안내, Wi-Fi·모바일 데이터 차단 후 오류 안내와 재연결 복구를 요청했고 “1,2 모두 확인했어”라는 답변을 받았다. 해당 iPhone 실기기 항목을 사용자 확인으로 통과 처리한다. 로그아웃 직후 뒤로가기 캐시 노출 여부까지 확인한 것으로 확대 해석하지 않는다.
- iPhone의 주요 흐름 확인 후 Android 실기기 검증을 재개했다. `adb devices -l`에서 연결 기기가 없어 USB 데이터 연결·디버깅 승인을 요청했다. Android에는 공통 시작 URL 수정이 반영된 APK를 새로 빌드하여 설치해야 하며, iOS 전용 지도 수정이 Android에서도 적용된 것으로 간주하지 않는다.
- 공통 시작 URL 수정이 반영된 Android Debug APK 재빌드는 `BUILD SUCCESSFUL`로 완료했다. 이후 사용자가 “안드로이드는 추후에 하자. 우선 iphone으로 작업하고 테스트 진행하자”라고 결정했으므로 Android 연결·설치·실기기 검증을 보류한다. 사용자 재개 요청 전에는 Android 연결을 다시 요구하지 않는다. iPhone의 인증 취소 복귀, 키보드·안전 영역 등 남은 확인을 진행한다.


## 2026-10-12 브랜드에서 로그인으로 이어지는 진입 리듬

- 사용자 요청: `로그인 화면을 불러오고 있어요` 대신 처음부터 브랜드를 보여 주고 로그인 버튼을 부드럽게 공개한다.
- 웹: 준비 중·로그인 화면은 `EntryBrand`/`EntryCourt`와 같은 행동 영역 높이를 공유한다. 준비 후 400ms의 호흡, 700ms의 버튼 등장만 사용하고 로고를 재등장시키지 않는다. reduced-motion에서는 바로 표시한다.
- iOS: OS LaunchScreen과 최초 로딩 덮개를 그린 브랜드로 교체했다. 네트워크 대기를 포함해 최소 650ms 표시 후 준비된 웹으로 교차 전환한다. 동작 줄이기는 인위적 대기를 생략한다. 20초 재시도·기존 WKWebView·카카오 인증·지도 플러그인은 유지한다.
- 웹과 iOS가 서로 다른 글꼴로 로고를 그려 겹치지 않도록 같은 Pretendard Black 기반 벡터를 SVG/PDF로 사용한다. 글꼴 라이선스는 `public/images/brand/wordmark-LICENSE.txt`에 보관한다.
- 최초 웹 준비 시 공개 UI 요소의 위치만 읽어 안전 영역·폰트 차이를 250ms 동안 맞춘 뒤 350ms 교차 전환한다. 같은 origin의 문서에만 `data-rally-native-reveal`을 설정해 버튼을 나중에 공개한다. 인증 정보는 전달하지 않으며, 중단될 때도 2.5초 복구 타이머로 버튼이 계속 숨겨지지 않게 한다.
- prepare는 생성된 SceneDelegate·LaunchScreen·로고 에셋에 별도 수정이 있으면 덮어쓰지 않는다. 시제품 검사 17개, 웹 진입 E2E 3개(320/375px·지연·오류·동작 줄이기), 린트·타입 검사·웹 프로덕션 빌드 및 iOS Debug/Release 시뮬레이터 빌드 통과. 일반 단위 검사 429개 통과, DB가 필요한 117개는 이번 로컬 검사에서 제외됐다.
- 검증용 시뮬레이터 복사본은 로컬 서버·별도 bundle ID를 사용한다. 초기 검은 구간은 테스트용 복사본의 미서명 리소스에 대한 SplashBoard 보안 오류(-67056)로 확인했다. 임시 서명을 적용한 뒤 검은 화면 없이 브랜드부터 시작하는 것을 확인했으며, 제품의 인증·보안 설정을 약화하지 않는다.
- 운영 웹 배포와 실제 iPhone 재설치는 이번 수정 이후 아직 수행하지 않았다. 실기기에서 콜드 스타트·앱 복귀를 다시 확인해야 하며 시뮬레이터 결과를 실기기 성공으로 간주하지 않는다. Android 검증은 사용자 결정대로 보류한다.
