## 1. 결론과 범위

1인 운영을 위해 새 관리 시스템을 더 만들기보다 **운영·개발 DB 분리, 내부 관리자 지정, 백업·복구 준비**를 먼저 마친다. 현재 서비스는 응답하지만, 이 세 항목이 해결되기 전에는 실제 참가자를 받는 파일럿 준비가 끝났다고 볼 수 없다.

Vercel 설정·배포 기록, 운영 DB의 읽기 전용 조회, 로그인된 Neon 콘솔, 저장소 설정을 확인했다. 운영 데이터·권한·환경변수·복구 설정은 변경하지 않았고, 마이그레이션·배포·복구도 실행하지 않았다. 연결 문자열, 비밀번호, 개인별 거래·계정 정보는 이 문서에 남기지 않는다.

이 문서는 [9월 파일럿 점검](03-11-pilot-readiness.md)의 환경·권한·복구·배포 항목을 다시 확인한 결과다. 그 문서의 당시 이용자 수나 테스트 데이터 수를 현재 수치로 간주하지 않는다. 이번 점검은 약관·전체 기능·보안 전반에 대한 출시 인증이 아니다.

### 운영 DB를 함께 쓰는 경로

연결값은 메모리 안에서 호스트의 pooled 차이를 정규화하고 DB 이름을 비교했다. 단순히 환경변수 이름이 같아서 내린 결론이 아니다.

`prisma.config.ts`는 `DATABASE_URL_UNPOOLED`를 우선한다. **`DATABASE_URL` 하나만 개발용으로 바꾸면 마이그레이션은 여전히 운영 DB로 갈 수 있다.** 두 값을 함께 분리하고 실제 대상까지 확인해야 한다.

`package.json`의 `vercel-build`는 `prisma migrate deploy`를 포함한다. 현재 운영 배포 로그에서도 해당 빌드 명령과 마이그레이션 실행을 확인했다. 지금 설정으로 미리보기 배포를 하면 운영 DB 스키마를 먼저 바꿀 위험이 있으므로, 환경 분리 전에 보류 중인 변경을 배포하지 않는다.

### 내부 관리자

운영 DB에서 역할별 집계를 확인했으며 `INTERNAL_REVIEWER` 계정은 상태와 무관하게 0명이다. 활성 상태이면서 인증 계정이 연결된 내부 관리자도 0명이다. Vercel·Neon의 소유자 권한과 Rally On 앱 내부 권한은 별개다.

기존 `prisma/grant-internal-reviewer.ts`로 지정할 수 있으므로 관리자 임명 화면을 새로 만들 필요는 없다. 사용자가 실제 이용하는 앱 계정을 특정한 뒤, 해당 계정에만 역할을 부여하고 로그인해 업무 화면 접근을 확인한다. 이번 점검에서는 역할을 부여하지 않았다.

## 3. 백업과 복구

Neon 콘솔에서 다음을 확인했다.

- 프로젝트: `tennis-mate-db`, Free plan, PostgreSQL 18.
- 브랜치: 기본 `main`, 그리고 `e2e` (`Schema-only`, `Archived branch` 표시).
- 프로젝트 복구 이력 보관: 6시간.
- `main`의 Backup & Restore 화면에서 확인 시점인 10월 10일 오전 10시 33분경, 가장 오래된 복구 가능 시각은 같은 날 오전 4시 33분(GMT+9).
- `main`에는 저장된 스냅샷과 예약이 없음. 실제 복구는 실행하지 않음.

기존 `e2e` 브랜치가 있다는 사실만으로 개발 환경이 분리됐다고 볼 수 없다. 현재 Vercel 개발·미리보기 연결과 로컬 앱은 운영 DB를 가리킨다. 기존 `e2e` 브랜치의 현재 내용·사용 목적·연결 상태를 확인하기 전에 임의로 초기화하거나 재사용하지 않는다.

6시간 이력은 짧은 실수 복구에는 쓸 수 있지만, 밤사이 사고를 다음 날 발견하는 경우에는 부족할 수 있다. **복구 메뉴가 있다는 것과 실제 복구를 검증했다는 것은 다르다.** 별도 보관한 백업의 존재도 이번 점검에서는 확인하지 못했다.

최소 후속 작업은 중요한 DB 변경 전 백업을 확보하고, 운영 DB를 덮어쓰지 않는 별도 대상으로 한 번 복원하여 스키마·주요 건수·앱 조회를 확인하는 것이다. 백업 저장 위치·접근 권한·보관 기간을 먼저 정하고, 개인정보가 담긴 원본을 저장소에 커밋하지 않는다. 예약 자동화·유료 플랜 전환은 이번 범위에 포함하지 않는다.

Neon의 과거 시점 복구는 보관 기간 안의 시점을 대상으로 하며, 실제 브랜치 복구는 현재 데이터를 대체한다. 콘솔의 Restore 버튼을 단순 점검 목적으로 실행하면 안 된다. 근거: [공식 이력 보관 설명](https://github.com/neondatabase/website/blob/main/content/docs/postgres/backup-restore/history-window.md), [공식 브랜치 복구 설명](https://github.com/neondatabase/website/blob/main/content/docs/postgres/backup-restore/branch-restore.md).

### 복구할 때

1. 먼저 오류 시각과 영향을 확인하고 추가 DB 쓰기·배포를 멈춘다. 앱 코드 되돌리기와 DB 복원은 별개다. 이번 마이그레이션은 새 테이블·타입 추가이므로 앱만 이전 배포로 되돌릴 때 테이블을 지울 필요는 없다.

4. Neon 이력 복구는 최근 6시간 이내에 한정된다. 저장한 스냅샷은 표시된 만료 시각 전까지 사용할 수 있으나, 현재 독립 브랜치 제한으로 별도 복원에 제약이 있다. `finalize`나 운영 main의 Restore를 점검 목적으로 실행하지 않는다.
5. 별도 복원본 검증 후에만 서비스 연결 변경 또는 필요한 데이터 복구를 결정한다. 되돌리는 시점 이후 거래의 처리 방안을 정하지 않은 채 운영을 과거 상태로 덮어쓰지 않는다.

2. **운영 DB 클라이언트 재사용 누락 확인**: `src/server/db/prisma.ts`의 `getPrisma()`는 production에서 생성한 클라이언트를 저장하지 않아 호출마다 새 Prisma/pg pool을 만든다. 현재 일반 목록 요청 경로만 해도 사용자 확인·요청 제한·프로필·목록에서 여러 번 호출한다. 한국 Mac에서 같은 DB에 단일 Prisma로 `SELECT 1`을 반복한 결과 첫 요청 635 ms, 이후 76/73/74 ms였다. 이는 연결 재사용 효과를 보는 참고값이며 Vercel 개선 후 응답시간 예측값이 아니다.
3. **초기 목록의 순차 요청 확인**: `m3-home.tsx`는 `/api/v1/me` 완료 후 `/api/v1/matches`를 요청한다. 양쪽에서 인증·프로필 확인 비용이 발생한다.
4. Neon scale-to-zero는 한동안 미사용 후 첫 요청에 영향을 줄 수 있으나 이번 연속 3회 지연을 이것만으로 설명할 수 없다. 이번에는 Neon의 실제 suspend 시점/compute 지표를 측정하지 않았다.

### 추가 비용 없는 개선 권장 순서 (미적용)

1. 프로세스 안에서 Prisma/pg pool을 재사용한다. production에서도 같은 인스턴스를 반환하는 회귀 검증을 추가한다.
2. Vercel Functions를 기존 DB와 같은 `sin1`으로 배포한다. DB 이전은 필요 없다. Hobby에서도 단일 실행 지역을 선택할 수 있다. [공식 지역 설정](https://vercel.com/docs/functions/configuring-functions/region), [지역 목록](https://vercel.com/docs/regions).
3. 위 두 변경의 전후 latency를 먼저 비교하고, 남은 지연에 한해 초기 사용자·목록 조회의 중복/순차 대기를 줄인다. 사용자별 인증·정원 검증과 요청 제한을 제거하거나 공용 캐시에 섞지 않는다.
4. 서버를 계속 깨우기 위한 추가 크론은 권장하지 않는다. 무료 DB 가동량을 소비한다. 기존 금융 기한 크론은 별도 운영 정책에 따라 유지한다.

검증: `npm run check` 통과(린트·타입·단위 413개·프로덕션 빌드). 전용 테스트 DB가 없는 110개 DB 테스트는 건너뛰었으며, 위 운영 데이터의 읽기 전용 검증과 구분한다. 이번에는 iPhone 수동 화면 테스트를 새로 수행하지 않았다.

## 9. DB 연결·지역·첫 목록 조회 개선 (2026-10-10)

사용자가 §8의 권장 순서인 DB 연결 재사용 → 서버 지역 변경 → 첫 화면 조회 개선을 승인했다. 무료 요금제와 현재 DB를 유지하며, 스키마·금전 처리 정책·크론 주기는 변경하지 않는다.

- **연결 재사용**: `getPrisma()`가 production에서도 프로세스 안의 같은 Prisma/pg pool을 반환하도록 수정했다. 사용자 데이터나 트랜잭션을 공유 캐시에 저장하는 변경은 아니다. 별도 서버 인스턴스·콜드 스타트에서는 새 연결이 필요하다.
- **지역**: `vercel.json`에 단일 Functions 지역 `sin1`을 지정했다. 기존 싱가포르 Neon과 가까운 서버에서 실행하며, DB 이전·새 리소스·유료 전환은 없다. 프로젝트 기본값보다 배포 설정이 우선한다.
- **첫 목록**: 홈 서버 페이지의 기존 계정 조회에 온보딩 상태를 함께 읽어 첫 화면을 결정한다. 완료한 사용자는 브라우저에서 `/me`를 다시 기다리지 않고 `/matches`를 조회한다. 목록 API의 인증·계정 상태·프로필·요청 제한 검증은 유지한다. 비로그인·세션 만료는 진입 화면, 프로필 누락은 온보딩, 이용 제한 계정은 거래 확인 화면으로 연결한다.
- **온보딩 복구**: 완료 시각이 있지만 프로필이 누락된 계정에서 완료 화면과 홈을 반복하지 않고 프로필을 다시 작성하도록 했다.
- **검증**: 린트·타입·프로덕션 빌드 및 단위 417개 통과. 운영과 분리한 임시 로컬 PostgreSQL E2E DB에 35개 마이그레이션을 적용하고 DB 통합 110개도 통과했다. 홈 브라우저 회귀 7개(중복 요청 없음, 비로그인, 이용 제한, 세션 만료, 오류 재시도, 프로필 누락, 신규 온보딩→목록)가 통과했다.
- **검증 환경**: 사용 중인 3103 개발 서버와 충돌하지 않도록 빌드된 앱을 3100 포트에서 실행했다. 로컬 production 테스트의 `AUTH_TRUST_HOST` 누락으로 발생한 첫 인증 실패는 테스트 서버 설정을 보완한 뒤 재검증했다. 운영 인증 설정을 변경하지 않았다.
- **배포 직전 기준값**: 한국 Mac에서 운영 `/api/health`를 순차 3회 호출한 TTFB는 1,819 / 1,878 / 1,843 ms(기존 `iad1`, 커밋 `75888e6`)였다. 로그인 후 전체 화면 속도나 부하 테스트 수치와 구분한다.

운영 반영 후 실제 `x-vercel-id`의 실행 지역과 같은 health 요청 응답 시간을 확인한다. Claude의 미커밋 네이티브 앱·푸시 문서는 이번 커밋과 배포에 포함하지 않는다.

## 10. 운영 테스트 데이터 정리 (2026-10-14)

사용자가 불필요한 테스트 데이터와 본인 계정으로 개설한 일반·코트 매칭의 삭제를 요청했다. 닉네임·카카오 인증 연결·내부 관리자 권한을 대조해 본인 계정을 확인하고, 기존 시드 코드의 고정 ID·생성 표시로 가상 데이터를 구분했다. 전체 초기화나 제목 검색만으로 삭제하지 않았다.

- 삭제: 일반 매칭 **10개**(본인 개설 4개 포함), 코트 매칭 **6개**, 연결 신청 **7건**, 테스트 알림 **15건**. 본인 개설 코트 매칭은 없었다.
- 함께 정리: 가상 코트·코트 단위·운영자 등록 각 **11건**, 시간대 **6건**, 로그인 연결이 없는 가상 계정·프로필 각 **25건**, 연결 목적·시간대 상태 이력. 실제 인증 계정은 삭제 대상에서 제외했다.
- 신청 7건 중 본인 신청 4건은 철회 상태이며 실제 입금·환불 기록이 없었다. 나머지 3건은 `seed-court-match`가 생성한 가상 신청이다. 이 중 18,000원 수령 표시는 시드의 확정 상태를 과거 마이그레이션이 이관한 값으로 확인했다. 실제 수령·환불 송금·협의·문의 기록은 없었다. 실사용자의 금전 이력을 정리한 것으로 해석하지 않는다.
- 보존: 본인 계정·카카오 인증 연결·테니스 프로필·내부 관리자 권한, 기존 공지 2건, 본인 증빙 업로드 기록 1건, 지역 코드·마이그레이션 및 그 밖의 대상 외 테이블. 신규 신청·거래·계정 변경 등 백업 이후 차이가 있으면 전체 작업을 중단하도록 검사했다.
- 복구 준비: 일관된 스냅샷의 전체 백업을 로컬 `.vercel/ops-backups/test-cleanup-20261014.dump`에 보관했다. 폴더 700·파일 600 및 Git 제외를 유지한다. 비밀값·백업 원문·개인별 식별자는 문서나 커밋에 넣지 않는다. 별도 로컬 PostgreSQL에 복원해 **45개 테이블의 건수와 모든 행의 해시가 일치**함을 확인했다.
- 검증: 복원 DB에서 먼저 같은 정리를 실행하고 보존 자료의 불변을 확인한 뒤 운영 DB에 하나의 트랜잭션으로 적용했다. 새 읽기 전용 연결로 45개 테이블의 최종 결과를 재확인했다. 현재 일반·코트 매칭과 신청은 0건이며 본인 계정·프로필·인증 연결은 각 1건이다. 앱 기능·스키마 수정이 없는 데이터 정리이므로 앱 빌드·전체 단위 검사는 반복하지 않았다.
- 임시 복원 DB와 이번 작업용 운영 환경변수 파일은 검증 후 제거한다. 보호된 백업·삭제 대상과 검증 결과만 로컬에 보관하며, 기존 백업과 함께 2026-10-17에 보존 필요를 재검토한다. 자동 파기는 설정하지 않았다.

운영 DB에 즉시 반영되므로 웹 새로고침 또는 iPhone 앱 재실행으로 확인할 수 있다. 앱 재설치·DB 마이그레이션·새 운영 배포는 필요 없다. 이후 테스트 데이터가 필요하면 새 요청으로 범위를 정하며 기존 시드를 자동 재실행하지 않는다.
