## 1. 결론과 범위

1인 운영을 위해 새 관리 시스템을 더 만들기보다 **운영·개발 DB 분리, 내부 관리자 지정, 백업·복구 준비**를 먼저 마친다. 현재 서비스는 응답하지만, 이 세 항목이 해결되기 전에는 실제 참가자를 받는 파일럿 준비가 끝났다고 볼 수 없다.

Vercel 설정·배포 기록, 운영 DB의 읽기 전용 조회, 로그인된 Neon 콘솔, 저장소 설정을 확인했다. 운영 데이터·권한·환경변수·복구 설정은 변경하지 않았고, 마이그레이션·배포·복구도 실행하지 않았다. 연결 문자열, 비밀번호, 개인별 거래·계정 정보는 이 문서에 남기지 않는다.

이 문서는 [9월 파일럿 점검](03-11-pilot-readiness.md)의 환경·권한·복구·배포 항목을 다시 확인한 결과다. 그 문서의 당시 이용자 수나 테스트 데이터 수를 현재 수치로 간주하지 않는다. 이번 점검은 약관·전체 기능·보안 전반에 대한 출시 인증이 아니다.

### 운영 DB를 함께 쓰는 경로

연결값은 메모리 안에서 호스트의 pooled 차이를 정규화하고 DB 이름을 비교했다. 단순히 환경변수 이름이 같아서 내린 결론이 아니다.

`prisma.config.ts`는 `DATABASE_URL_UNPOOLED`를 우선한다. **`DATABASE_URL` 하나만 개발용으로 바꾸면 마이그레이션은 여전히 운영 DB로 갈 수 있다.** 두 값을 함께 분리하고 실제 대상까지 확인해야 한다.

`package.json`의 `vercel-build`는 `prisma migrate deploy`를 포함한다. 현재 운영 배포 로그에서도 해당 빌드 명령과 마이그레이션 실행을 확인했다. 지금 설정으로 미리보기 배포를 하면 운영 DB 스키마를 먼저 바꿀 위험이 있으므로, 환경 분리 전에 보류 중인 변경을 배포하지 않는다.

### 내부 관리자

운영 DB에서 역할별 집계를 확인했으며 `INTERNAL_REVIEWER` 계정은 상태와 무관하게 0명이다. 활성 상태이면서 인증 계정이 연결된 내부 관리자도 0명이다. Vercel·Neon의 소유자 권한과 Rally On 앱 내부 권한은 별개다.

기존 `prisma/grant-internal-reviewer.ts`로 지정할 수 있으므로 관리자 임명 화면을 새로 만들 필요는 없다. 사용자가 실제 이용하는 앱 계정을 특정한 뒤, 해당 계정에만 역할을 부여하고 로그인해 업무 화면 접근을 확인한다. 이번 점검에서는 역할을 부여하지 않았다.

## 3. 백업과 복구

Neon 콘솔에서 다음을 확인했다.

- 프로젝트: `tennis-mate-db`, Free plan, PostgreSQL 18.
- 브랜치: 기본 `main`, 그리고 `e2e` (`Schema-only`, `Archived branch` 표시).
- 프로젝트 복구 이력 보관: 6시간.
- `main`의 Backup & Restore 화면에서 확인 시점인 10월 10일 오전 10시 33분경, 가장 오래된 복구 가능 시각은 같은 날 오전 4시 33분(GMT+9).
- `main`에는 저장된 스냅샷과 예약이 없음. 실제 복구는 실행하지 않음.

기존 `e2e` 브랜치가 있다는 사실만으로 개발 환경이 분리됐다고 볼 수 없다. 현재 Vercel 개발·미리보기 연결과 로컬 앱은 운영 DB를 가리킨다. 기존 `e2e` 브랜치의 현재 내용·사용 목적·연결 상태를 확인하기 전에 임의로 초기화하거나 재사용하지 않는다.

6시간 이력은 짧은 실수 복구에는 쓸 수 있지만, 밤사이 사고를 다음 날 발견하는 경우에는 부족할 수 있다. **복구 메뉴가 있다는 것과 실제 복구를 검증했다는 것은 다르다.** 별도 보관한 백업의 존재도 이번 점검에서는 확인하지 못했다.

최소 후속 작업은 중요한 DB 변경 전 백업을 확보하고, 운영 DB를 덮어쓰지 않는 별도 대상으로 한 번 복원하여 스키마·주요 건수·앱 조회를 확인하는 것이다. 백업 저장 위치·접근 권한·보관 기간을 먼저 정하고, 개인정보가 담긴 원본을 저장소에 커밋하지 않는다. 예약 자동화·유료 플랜 전환은 이번 범위에 포함하지 않는다.

Neon의 과거 시점 복구는 보관 기간 안의 시점을 대상으로 하며, 실제 브랜치 복구는 현재 데이터를 대체한다. 콘솔의 Restore 버튼을 단순 점검 목적으로 실행하면 안 된다. 근거: [공식 이력 보관 설명](https://github.com/neondatabase/website/blob/main/content/docs/postgres/backup-restore/history-window.md), [공식 브랜치 복구 설명](https://github.com/neondatabase/website/blob/main/content/docs/postgres/backup-restore/branch-restore.md).

### 복구할 때

1. 먼저 오류 시각과 영향을 확인하고 추가 DB 쓰기·배포를 멈춘다. 앱 코드 되돌리기와 DB 복원은 별개다. 이번 마이그레이션은 새 테이블·타입 추가이므로 앱만 이전 배포로 되돌릴 때 테이블을 지울 필요는 없다.
2. 복구 전 현재 DB도 백업한다. 사고 이후의 정상 입금·환불·문의 기록이 사라지지 않도록 비교 자료를 확보한다.
3. 기본 선택은 백업을 **빈 별도 DB**에 복원하는 것이다. 자격 증명은 보호된 환경변수로 주입하고 명령줄·로그·문서에 쓰지 않는다. `pg_restore --exit-on-error --no-owner --no-privileges --dbname=<별도 DB> <백업 파일>`로 복원한 뒤 테이블 건수와 중요 거래 상태를 비교한다.
4. Neon 이력 복구는 최근 6시간 이내에 한정된다. 저장한 스냅샷은 표시된 만료 시각 전까지 사용할 수 있으나, 현재 독립 브랜치 제한으로 별도 복원에 제약이 있다. `finalize`나 운영 main의 Restore를 점검 목적으로 실행하지 않는다.
5. 별도 복원본 검증 후에만 서비스 연결 변경 또는 필요한 데이터 복구를 결정한다. 되돌리는 시점 이후 거래의 처리 방안을 정하지 않은 채 운영을 과거 상태로 덮어쓰지 않는다.
